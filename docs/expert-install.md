# 🛠️ Экспертная (ручная) установка Ubuntu 26.04 LTS

## 📖 Введение

Документ описывает архитектуру и процесс сборки экспертной рабочей станции на базе **Ubuntu 26.04 LTS (Resolute Raccoon)**. Станция предназначена для DevOps и NetOps-инженеров и строится по принципам детерминизма, воспроизводимости и минимальной поверхности атаки. Сборка ведётся с нуля через `debootstrap`; шифрование диска выполняется в LUKS2; стек хранения строится на LVM поверх LUKS и XFS; Snap блокируется на уровне APT; NetworkManager не используется — сетевой стек опирается на `systemd-networkd` и `systemd-resolved`. Пользовательские фоновые процессы изолируются в S6 Supervisor, а Systemd отвечает только за базовый уровень (PID 1, `udev`, `logind`, `cgroups`, файловые системы, сеть). Резервное копирование автоматизировано через `restic`, обновления безопасности — через `unattended-upgrades`, а загрузка возможна с предыдущего ядра.

## 🎯 Выбор Ubuntu

Ubuntu 26.04 LTS выбрана по трём практическим причинам, напрямую связанным с ролью станции.

**Первая — предсказуемый жизненный цикл и инфраструктура безопасности.** LTS-релизы Ubuntu получают пять лет основной поддержки, а с Ubuntu Pro — до десяти лет расширенных security-обновлений, включая патчи ядра и соответствие FIPS 140-3 и CIS Benchmark. Для рабочей станции, которая собирается один раз и эксплуатируется годами, это означает, что security-канал (`resolute-security`) остаётся актуальным без пересборки на новый релиз каждые девять месяцев.

**Вторая — совместимость с индустриальным стеком.** Ubuntu — стандартная платформа для контейнеров (`containers`), виртуализации (`libvirt`), Kubernetes и CI/CD-агентов. Образы, Helm-чарты, инструкции и скрипты в подавляющем большинстве случаев предполагают Ubuntu или Debian как целевую систему. Станция DevOps/NetOps, собранная на Ubuntu, минимизирует трение при запуске тех же инструментов, которые используются в production.

**Третья — зрелость механизмов, на которых строится hardened-сборка.** `debootstrap` — родной инструмент Debian/Ubuntu. `apt` с pinning, DEB822, `unattended-upgrades` и `systemd`-стек (включая `systemd-networkd`, `systemd-resolved`, `systemd-cryptenroll`) доступны в актуальных версиях без сторонних репозиториев. Secure Boot поддерживается через `shim-signed` и `grub-efi-amd64-signed` из официального архива. Ни одна из этих подсистем не требует PPA или ручной сборки — всё поставляется Canonical и подписано ключами архива.

Альтернативы рассматривались и отклонены. Debian стабилен, но заморозка пакетов делает его менее удобным для свежего оборудования (AX210, RTX 3070) и новых версий `systemd`. RHEL/CentOS Stream дают XFS и SELinux «из коробки», но `debootstrap`-подход и экосистема APT для тонкой сборки минимальной системы там отсутствуют. Arch даёт контроль, но не даёт предсказуемости security-канала. Ubuntu 26.04 LTS занимает точку, где детерминизм сборки, свежесть ядра и долгосрочная поддержка совпадают.

## 💿 Необходимость LiveCD

`debootstrap` — утилита, которая создаёт файловую систему целевой системы изнутри уже работающей Linux-системы. Ей нужны: работающее ядро, сетевой стек, `debootstrap` в `PATH`, утилиты разметки (`cfdisk`, `parted`), `cryptsetup`, `lvm2`, `mkfs.*` и chroot-окружение. Всё это отсутствует на «голом железе» до установки операционной системы. Следовательно, требуется промежуточная среда — LiveCD (или LiveUSB).

Live-образ Ubuntu предоставляет именно то, что нужно: загружаемое ядро с поддержкой UEFI, Secure Boot (через shim), NVMe, LUKS2 и LVM, а также полный набор утилит для разметки и шифрования. `debootstrap` в Live-среде устанавливается одной командой (`apt install debootstrap`) и сразу готов к работе. Альтернативы — загрузка по сети (netboot) или установка с другой Linux-системы — существуют, но LiveUSB остаётся наиболее воспроизводимым и предсказуемым вариантом: версия ядра и набор утилит фиксированы образом, а не зависят от состояния уже установленной системы.

Стандартный установщик Ubuntu (`ubiquity` / `subiquity`) для этой задачи не подходит: он создаёт систему по заранее определённому сценарию, ставит Snap, NetworkManager, `cloud-init` и прочие компоненты, которые в hardened-станции не нужны. `debootstrap` даёт полный контроль над каждым установленным пакетом и каждым байтом конфигурации. Цена — ручная разметка и ручная настройка загрузчика, но именно это и является целью: система собирается из явно перечисленных компонентов, а не из пресета.

Образ записывается на USB-носитель (например, `dd` или `balenaEtcher`), после чего машина загружается в режиме UEFI. Проверка режима выполняется командой `[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS`. Если выводится `BIOS`, загрузка прошла в legacy-режиме, и дальнейшие шаги (EFI-раздел, `grub-efi-amd64-signed`, `shim-signed`) не будут работать корректно. Secure Boot на время установки можно оставить включённым: подписанный shim Live-образа загрузится, а целевая система получит собственный подписанный загрузчик на Этапе 2.

### 🔌 SSH-доступ к среде установки

Сборка через `debootstrap` требует выполнения десятков команд в терминале установочной среды. Работа напрямую с консоли LiveCD неудобна: ограниченная история, отсутствие буфера обмена, невозможность копировать длинные команды из документации. Поэтому установочная среда поднимает SSH-сервер, и все дальнейшие операции выполняются с другой машины по сети. Это не обязательный шаг, но он радикально снижает вероятность опечаток и позволяет держать документацию открытой рядом с терминалом.

В Live-среде Ubuntu по умолчанию нет `openssh-server`, а root-логин по SSH заблокирован. Минимальный набор действий в терминале LiveCD:

```bash
sudo apt update && sudo apt install -y openssh-server
sudo passwd ubuntu          # задать пароль root для входа по SSH
sudo systemctl start ssh
ip -br addr               # узнать IP-адрес установочной машины
```

После этого с рабочей машины выполняется вход:

```bash
ssh ubuntu@<IP-АДРЕС>
```

SSH-сервер и пароль ubuntu существуют только в оперативной памяти LiveCD. После перезагрузки в собранную систему они исчезают, никаких следов в целевой системе этот шаг не оставляет. Временный SSH-доступ действует только в доверенном сегменте сети (локальная лаборатория, VLAN управления).

## 🖥️ Этап 0: Инвентаризация аппаратной платформы

Инвентаризация выполняется до любых операций с диском и до установки пакетов. На этом шаге фиксируется фактический состав оборудования: процессор, GPU и iGPU, сетевые адаптеры, Wi-Fi и Bluetooth, NVMe-контроллер, аудиокодек, камера и TPM. Полученный «слепок» определяет дальнейшие решения — от выбора firmware-пакетов и драйверов до того, какие компоненты заведомо не нужны в системе. Ошибка на этом этапе проявляется позже: либо лишними пакетами с дополнительной поверхностью атаки, либо отсутствующей прошивкой, без которой устройство не поднимается после первой загрузки. Поэтому инвентаризация рассматривается не как справочный шаг, а как входной контракт для всех последующих этапов сборки.

### 🔍 0.1 Зачем нужна инвентаризация

Прежде чем размечать диск, фиксируется реальная конфигурация железа. Это критично по трём причинам.

**Выбор firmware-пакетов.** Прошивки в Linux поставляются отдельными пакетами (`linux-firmware-*`), и каждый из них закрывает свой класс устройств: `linux-firmware-intel-wireless` — Wi-Fi и Bluetooth от Intel, `linux-firmware-realtek` — сетевые и NVMe-контроллеры Realtek, `linux-firmware-nvidia-graphics` — GSP-прошивки для новых GPU NVIDIA. Установка лишних firmware-пакетов — это лишняя поверхность атаки и лишние мегабайты в образе, которые никогда не загрузятся.

**Выбор драйверов.** Наличие или отсутствие iGPU определяет, нужен ли `va-driver-all` (аппаратное видеоускорение Intel/AMD) и `linux-firmware-intel-graphics`. Наличие дискретной NVIDIA определяет, нужен ли проприетарный драйвер и какие именно модули ядра будут загружаться (`nouveau` или `nvidia`). Наличие или отсутствие модема определяет, нужен ли `modemmanager`.

**Документирование.** «Слепок» железа сохраняется в `/tmp/hw-info.txt` — при отладке через месяцы будет точно известно, какой модуль ядра и какая прошивка отвечали за Wi-Fi, Bluetooth, звук или камеру. Без этого «слепка» диагностика превращается в угадывание.

### 🧩 0.2 Состав аппаратной платформы

Собранное железо (по `lspci`, `lsusb`, `/proc/asound/cards`):

| Компонент | Модель | Что даёт для сборки |
| :--- | :--- | :--- |
| **CPU** | Intel Core i5-11400 (Rocket Lake, 6C/12T) | `thermald`, `intel-microcode` (транзитивно). `amd64-microcode` не нужен, но приедет с ядром. |
| **iGPU** | Отсутствует (отключён в BIOS) | `va-driver-all` **не нужен**. `linux-firmware-intel-graphics` — тоже. |
| **GPU** | NVIDIA GeForce RTX 3070 (GA104, LHR) | Драйвер ставится отдельно. `linux-firmware-nvidia-graphics` **не нужен** — GSP-прошивка идёт в самом драйвере Nvidia. |
| **Wi-Fi + BT** | Intel AX210 (Wi-Fi 6E, BT 5.4) | `linux-firmware-intel-wireless` + `linux-firmware-intel-misc` (BT-прошивки). Интерфейс: `wlp3s0`. |
| **Ethernet** | Intel I219-V (`e1000e`) | Прошивка в ядре, `linux-firmware-realtek` **не нужен**. |
| **NVMe** | ADATA SX8100NP (контроллер Realtek RTS5762) | Прошивка в ядре, `linux-firmware-realtek` не нужен и для NVMe. |
| **Audio** | Intel HDA (ALC662) + NVIDIA HDMI + BRIO USB | `firmware-sof-signed` **нужен** (`snd_sof_intel_hda` реально загружен). |
| **Камера** | Logitech BRIO (USB, UVC) | Стандартный `uvcvideo`. `libcamera-ipa`, `pipewire-libcamera`, `gstreamer1.0-libcamera` **не нужны**. Нужен `v4l-utils` для диагностики. |
| **TPM** | TPM 2.0 (`/dev/tpm0` есть) | Опционально `tpm2-tools` для LUKS-разблокировки через `systemd-cryptenroll`. |

### 📜 0.3 Скрипт инвентаризации

Перед разметкой сохраняется «слепок» железа — он пригодится при отладке и для документирования:

```bash
{
  echo "===== CPU ====="            ; lscpu | grep -E 'Model name|Vendor|Thread|Core'
  echo "===== PCI ====="            ; lspci -nn
  echo "===== USB ====="            ; lsusb
  echo "===== Block devices ====="  ; lsblk -o NAME,SIZE,TYPE,TRAN,MODEL
  echo "===== Network ====="        ; ip -br link
  echo "===== Wi-Fi ====="          ; iw dev 2>/dev/null
  echo "===== Bluetooth ====="      ; hciconfig -a 2>/dev/null
  echo "===== Sound ====="          ; cat /proc/asound/cards 2>/dev/null
  echo "===== TPM ====="            ; ls /sys/class/tpm/ 2>/dev/null
  echo "===== Kernel modules =====" ; lsmod | grep -E '^(iwlwifi|e1000e|amdgpu|i915|nouveau|nvidia|snd_hda|btusb)'
} 2>&1 | tee /tmp/hw-info.txt
```

Вывод сохраняется в `/tmp/hw-info.txt`. При повторении руководства на другом железе этот файл — отправная точка для адаптации списка пакетов и firmware. Если позже Wi-Fi или BT перестанут работать, файл точно укажет, какой именно модуль ядра и какая прошивка за них отвечали.

### ⚙️ 0.4 Влияние железа на выбор пакетов

Конфигурация железа напрямую определяет список пакетов. Ниже — соответствие между компонентом и решением.

**Intel CPU.** `thermald` управляет температурой через MSR-регистры, актуален только для Intel. `intel-microcode` приходит транзитивно с ядром; `amd64-microcode` не нужен, но также приедет с ядром и будет проигнорирован на Intel.

**Отсутствие iGPU.** Пакеты `va-driver-all` (VA-API для Intel/AMD iGPU) и `linux-firmware-intel-graphics` не устанавливаются: аппаратного видеоускорения через iGPU нет, а дискретная NVIDIA использует собственный драйвер.

**NVIDIA RTX 3070.** Драйвер ставится отдельно после базовой системы (проприетарный `nvidia-driver-*` или открытый `nouveau` — выбор фиксируется в отдельном решении). `linux-firmware-nvidia-graphics` не нужен: GSP-прошивка поставляется в самом пакете драйвера Nvidia, а не в `linux-firmware`.

**Intel AX210.** Требует `linux-firmware-intel-wireless` (Wi-Fi 6E, файлы `iwlwifi-ty-a0-gf-a0-*.ucode`) и `linux-firmware-intel-misc` (Bluetooth-прошивки). Модуль ядра — `iwlwifi`, интерфейс `wlp3s0`.

**Intel I219-V.** Прошивка встроена в ядро (модуль `e1000e`), отдельный firmware-пакет не требуется. `linux-firmware-realtek` не нужен ни для Ethernet, ни для NVMe (контроллер RTS5762 тоже обходится без внешней прошивки).

**Intel HDA + SoF.** `snd_sof_intel_hda` реально загружается, поэтому `firmware-sof-signed` обязателен. Без него звук работает только через legacy HDA-путь, а на некоторых кодеках (включая ALC662) возможны проблемы с микрофоном.

**Logitech BRIO.** Стандартная UVC-камера, работает через `uvcvideo`. Пакеты `libcamera-ipa`, `pipewire-libcamera`, `gstreamer1.0-libcamera` нужны только для ISP-пайплайнов ноутбучных камер (IPU6 и подобных) — на BRIO они не задействованы. `v4l-utils` нужен для диагностики (`v4l2-ctl --list-devices`).

**TPM 2.0.** Опционально `tpm2-tools` позволяет разблокировать LUKS через `systemd-cryptenroll --tpm2-device=auto`. В базовой поставке TPM не используется для GPG/SSH, поэтому `tpm2daemon` (часть `tpm2-abrmd`) не устанавливается.

### 💾 0.5 Firmware-стратегия

В 26.04 метапакет `linux-firmware` и все его подпакеты приезжают **транзитивно** через `linux-generic-hwe-26.04`, потому что firmware объявлен жёстким `Depends`. Бороться с метапакетом через pinning рискованно: сломает автообновления ядра. Явное перечисление `linux-firmware-misc`, `linux-firmware-intel-wireless`, `linux-firmware-intel-misc` в команде установки — это документирование намерения, а не экономия места.

Сознательно **не устанавливаются**: `linux-firmware-realtek` (нет устройств Realtek, требующих внешней прошивки), `linux-firmware-nvidia-graphics` (GSP-прошивка в драйвере Nvidia), `linux-firmware-intel-graphics` (iGPU отключён). Если позже добавится устройство, требующее одну из этих прошивок, пакет ставится точечно — но не «на всякий случай» заранее.

### 🧭 0.6 Сегрегация ответственности: Systemd vs S6

В основе системы лежит принцип строгой сегрегации ответственности между компонентами.

**Уровень 1: Systemd (PID 1).** Отвечает только за базовые вещи: `udev`, `logind` (критично для прав доступа к GPU и ввода), `cgroups`, файловые системы и сеть через `systemd-networkd` + `systemd-resolved`. NetworkManager не используется — для стационарного ПК с одним Wi-Fi и одним Ethernet детерминированная связка `systemd-networkd` + `wpa_supplicant` + `systemd-resolved` покрывает 100% задач, а конфигурация — файлы в `/etc/systemd/network/`, которые можно версионировать. NM — удобная, но тяжёлая надстройка, добавляющая ещё один канал обновлений и ещё одну точку, где поведение системы перестаёт быть предсказуемым.

**Уровень 2: Wayland + Qtile.** Занимается исключительно управлением окнами и тайлингом. Qtile не запускает фоновые демоны.

**Уровень 3: S6 Supervisor.** Все пользовательские фоновые процессы (уведомления, буфер обмена, аудио, политики безопасности, keyring) запускаются и контролируются `s6-svscan` в рамках сессии пользователя. Это даёт микросекундный запуск, автоматический перезапуск упавших сервисов и чистые логи.

## 💽 Этап 1: Разметка и шифрование (LUKS2 + LVM + XFS)

Разметка диска — первый шаг, который необратимо влияет на всё остальное: на схему загрузки, на расположение ключевых материалов, на поведение GRUB и Secure Boot, на то, как система переживает обновления ядра. Ошибка здесь стоит дороже всего, потому что исправляется только пересборкой. Поэтому разметка выполняется осознанно и по фиксированной схеме, а не через автоматический установщик.

Схема состоит из трёх разделов GPT. Первый раздел — EFI System Partition размером 1 ГБ, отформатированный в `vfat`. Второй — `/boot` размером 1 ГБ, отформатированный в `ext4`. Третий — остаток диска, внутри которого размещается контейнер LUKS2, а поверх него — LVM с файловыми системами XFS. Такая иерархия не случайна: каждый уровень решает свою задачу и не дублирует соседний.

> [!question] Почему GPT, а не MBR?
> GPT — стандарт для UEFI-систем. Он не имеет ограничения в 2 ТБ на раздел, поддерживает до 128 разделов по умолчанию.
> Также GPT хранит резервную копию таблицы разделов в конце диска и использует CRC32 для проверки целостности файлов.
> MBR для UEFI-загрузки технически возможен, но это legacy-путь с дополнительными ограничениями и без выгоды.

> [!question] Почему /boot вынесен отдельно и не зашифрован?
> GRUB должен прочитать ядро и initramfs до того, как станет доступен криптографический стек для разблокировки LUKS.
> Если `/boot` находится внутри зашифрованного тома, GRUB вынужден либо нести собственный модуль LUKS, либо полагаться на внешний `/boot`.
> Отдельный незашифрованный `/boot` с `ext4` — компромисс, который даёт максимальную совместимость с GRUB, Secure Boot и обновлениями ядра.
> Целостность `/boot` при этом защищается Secure Boot и подписью ядра, а конфиденциальность содержимого (ядро, initramfs) не является секретом.

> [!question] Почему EFI-раздел отдельный и в vfat?
> UEFI-прошивка умеет читать только FAT-разделы. `vfat` (`mkfs.vfat -F32`) — единственная файловая система, которую прошивка гарантированно понимает на любой аппаратной платформе.
> Размер 1 ГБ выбран с запасом: сюда попадают загрузчик, shim, подписанные ядра и, при необходимости, несколько версий initramfs.
> Меньший размер (стандартные 512 МБ) быстро заполняется при накоплении старых ядер, и обновление ядра падает на этапе `grub-install`.

```bash
# Проверка UEFI (ожидается UEFI)
[ -d /sys/firmware/efi ] && echo UEFI || echo BIOS

# Разметка: nvme0n1p1 — EFI 1G, nvme0n1p2 — /boot 1G, nvme0n1p3 — LUKS остаток
sudo cfdisk /dev/nvme0n1
```

`cfdisk` выбран как интерактивный инструмент разметки: он показывает таблицу разделов в понятном виде и не позволяет случайно перезаписать существующую схему без подтверждения. Для автоматизированной сборки его можно заменить на `sgdisk` с явными параметрами, но при первой сборке интерактивный режим снижает риск ошибки.

### 🔐 Контейнер LUKS2

Поверх третьего раздела создаётся контейнер LUKS2. LUKS2 — актуальный формат заголовка LUKS, в отличие от LUKS1 он поддерживает Argon2 как функцию вывода ключа, несколько ключевых слотов с разными типами (пароль, ключевой файл, TPM2, FIDO2), а также метаданные в формате JSON, которые можно проверять и резервировать. LUKS1 остаётся только для совместимости со старыми системами и не даёт ни одного преимущества на новой сборке.

```bash
sudo cryptsetup luksFormat \
  --type luks2 \
  --cipher aes-xts-plain64 \
  --key-size 512 \
  --hash sha512 \
  --iter-time 5000 \
  /dev/nvme0n1p3

sudo cryptsetup open /dev/nvme0n1p3 cryptroot
```

Параметры выбраны не по умолчанию, а осознанно:

- **`--type luks2`** — актуальный формат заголовка. Даёт Argon2id, несколько слотов, JSON-метаданные, возможность `cryptsetup luksDump` в читаемом виде.
- **`--cipher aes-xts-plain64`** — режим XTS с 64-битным tweak. Это стандарт для дискового шифрования: XTS специально спроектирован для блочных устройств и не имеет проблемы повторного использования IV, которая есть у CBC. `plain64` — формат tweak, совместимый с секторами диска.
- **`--key-size 512`** — для XTS ключ делится на две половины по 256 бит: одна для шифрования данных, другая для tweak. 512 бит общего ключа — стандартная и рекомендуемая конфигурация для AES-XTS.
- **`--hash sha512`** — хеш-функция для вывода ключа из пароля. SHA-512 работает эффективнее SHA-256 на 64-битных процессорах и даёт лучшую стойкость к коллизиям.
- **`--iter-time 5000`** — время в миллисекундах, которое `cryptsetup` тратит на калибровку Argon2. Пять секунд — компромисс: разблокировка при загрузке занимает заметное, но приемлемое время, а перебор пароля на атакующем оборудовании замедляется на порядки. Меньшее значение ускоряет загрузку, но снижает стоимость атаки; большее — наоборот.

После `luksFormat` контейнер открывается через `cryptsetup open`. С этого момента появляется устройство `/dev/mapper/cryptroot`, с которым работают LVM-инструменты. Открытие запрашивает пароль; для неинтерактивной сборки можно использовать ключевой файл, но на рабочей станции пароль остаётся основным методом, а TPM2 или FIDO2 добавляются позже как дополнительные слоты через `systemd-cryptenroll`.

### 🗄️ LVM и файловые системы

LVM поверх LUKS даёт то, чего не даёт прямая разметка: гибкое перераспределение места между томами, снимки (snapshots) для резервного копирования, тонкое выделение (thin provisioning) для виртуальных машин и контейнеров. На диске фиксированного размера LVM позволяет перерасти первоначальную оценку без пересборки: увеличить `root` за счёт `home`, добавить новый том под новый сценарий, сделать снимок перед рискованным обновлением.

```bash
sudo pvcreate /dev/mapper/cryptroot
sudo vgcreate vg0 /dev/mapper/cryptroot

# Под диск ~1TB
sudo lvcreate -L 100G -n root       vg0
sudo lvcreate -L 30G  -n var_log    vg0
sudo lvcreate -L 250G -n libvirt    vg0
sudo lvcreate -L 150G -n containers vg0
sudo lvcreate -l 100%FREE -n home   vg0
```

Разбиение на отдельные тома — не косметика, а элемент отказоустойчивости и безопасности. `root` отделён от `home`, чтобы заполнение домашнего каталога не приводило к отказу системы. `var_log` вынесен отдельно, чтобы журналы не могли занять место, нужное для работы сервисов, и чтобы к нему можно было применить отдельные квоты. `libvirt` и `containers` вынесены, потому что образы виртуальных машин и слои контейнеров растут быстро и непредсказуемо; их изоляция защищает корневую файловую систему от внезапного заполнения. `home` получает всё оставшееся место, потому что именно там ожидается основной рост пользовательских данных.

Размеры выбраны под диск около 1 ТБ. На меньшем диске пропорции сохраняются, но абсолютные значения уменьшаются; на большем — увеличиваются. Ключевой принцип: `root` не должен быть меньше 60–80 ГБ (обновления ядра, пакеты, `snap`-кэши — всё это живёт в `/`), `var_log` не должен быть меньше 20 ГБ (журналы systemd и audit при интенсивной работе занимают много), а `libvirt` и `containers` должны иметь запас, соответствующий планируемому количеству ВМ и образов.

```bash
sudo mkfs.xfs /dev/vg0/root
sudo mkfs.xfs /dev/vg0/var_log
sudo mkfs.xfs /dev/vg0/libvirt
sudo mkfs.xfs /dev/vg0/containers
sudo mkfs.xfs /dev/vg0/home

sudo mkfs.ext4 /dev/nvme0n1p2
sudo mkfs.vfat -F32 /dev/nvme0n1p1
```

XFS выбран для всех LVM-томов, включая `/`. Это не догма, а следствие конкретных требований. XFS даёт лучшую параллельность при одновременной записи из множества потоков, предсказуемое поведение при больших файлах (qcow2, слои образов, архивы) и эффективное использование пространства за счёт отложенного выделения (delayed allocation). Для `libvirt` и `containers` это особенно важно: там одновременно работают десятки процессов, каждый из которых пишет в свой файл. Для `root` и `home` XFS также подходит, но разница с ext4 там менее заметна.

ext4 оставлен только под `/boot`. Причина — максимальная совместимость с GRUB: `ext4` поддерживается всеми версиями GRUB без дополнительных модулей, а `xfs` требует загрузки модуля `xfs` в GRUB, что увеличивает размер загрузчика и создаёт дополнительную точку отказа. На разделе размером 1 ГБ преимущества XFS всё равно не проявляются, поэтому выбор в пользу ext4 здесь чисто практический.

`vfat -F32` для EFI-раздела — не выбор, а требование UEFI-спецификации. Прошивка не умеет читать ничего другого, и попытка использовать `ext4` или `xfs` на EFI-разделе приведёт к тому, что система не загрузится.

## 📦 Этап 2: Базовая система через debootstrap

После разметки и форматирования создаётся пустая иерархия каталогов, в которую будет установлена минимальная система. Порядок монтирования строго определён: родительские точки монтируются раньше дочерних. Если смонтировать `/mnt/home` до `/mnt`, то последующее монтирование `/mnt` скроет содержимое `/mnt/home`, и данные окажутся в корневой файловой системе, а не в отдельном томе. Это классическая ошибка при ручной сборке, и она проявляется только при следующей перезагрузке, когда том `/home` оказывается пустым.

```bash
sudo mount /dev/vg0/root /mnt
sudo mkdir -p /mnt/{boot,home,var/log,var/lib/libvirt,var/lib/containers}
sudo mount /dev/nvme0n1p2 /mnt/boot
sudo mkdir -p /mnt/boot/efi
sudo mount /dev/nvme0n1p1 /mnt/boot/efi
sudo mount /dev/vg0/home /mnt/home
sudo mount /dev/vg0/var_log /mnt/var/log
sudo mount /dev/vg0/libvirt /mnt/var/lib/libvirt
sudo mount /dev/vg0/containers /mnt/var/lib/containers
```

Каталоги создаются через `mkdir -p` до монтирования, потому что точка монтирования должна существовать. `/mnt/boot/efi` создаётся отдельно после монтирования `/boot`, потому что EFI-раздел вкладывается внутрь `/boot`, а не монтируется параллельно. Такая вложенность отражает реальную иерархию: EFI-раздел — часть загрузочной цепочки, а `/boot` — её продолжение.

`debootstrap` устанавливается в Live-среде отдельно: в минимальном образе Ubuntu его нет, а без него невозможна сборка целевой системы.

```bash
sudo apt update && sudo apt install -y debootstrap
```

`debootstrap` устанавливает в `/mnt` минимальный набор пакетов: ядро, `systemd`, `apt`, базовые утилиты. Вариант `minbase` означает, что устанавливается только `Priority: required` и `Priority: important` из основного репозитория, без `Recommends` и без дополнительных сервисов. Это даёт чистую основу, на которую затем накладывается точный список пакетов из Этапа 3.

```bash
sudo debootstrap \
  --arch=amd64v3 \
  --variant=minbase \
  --keyring=/usr/share/keyrings/ubuntu-archive-keyring.gpg \
  resolute /mnt http://ru.archive.ubuntu.com/ubuntu
```

**`--arch=amd64v3`** фиксирует не просто x86_64, а уровень микроархитектуры **x86-64-v3**. Это означает, что все пакеты, скачанные и установленные `debootstrap`, собраны с расчётом на наличие AVX, AVX2, BMI1, BMI2, FMA, MOVBE, F16C и LZCNT. По сравнению с базовым `amd64` (x86-64-v1) такой код может выполняться заметно быстрее на современных процессорах — особенно в задачах, где важна векторная обработка: сжатие, шифрование, работа с контейнерами и виртуальными машинами. Canonical развивает это направление с Ubuntu 25.10, и для 26.04 LTS архив `amd64v3` уже доступен как отдельный набор пакетов.

> [!danger] Ограничение amd64v3
> Пакеты, собранные для x86-64-v3, не запустятся на процессорах, которые не поддерживают этот уровень (например, на старых Intel до Haswell или на некоторых маломощных платформах).
> Для данной станции это ограничение неактуально: Intel Core i5-11400 (Rocket Lake) полностью поддерживает x86-64-v3.
> Если позже система будет переноситься на более старое железо, архитектуру придётся вернуть к `amd64` и пересобрать систему.

**`--keyring`** указывает на ключи проверки подписи пакетов; без него `debootstrap` использует ключи из хостовой системы, что на LiveCD может дать устаревший набор. **`resolute`** — кодовое имя релиза, соответствующее Ubuntu 26.04 LTS. Зеркало `http://ru.archive.ubuntu.com/ubuntu` выбрано по тем же причинам, что и для APT на Этапе 3.1: официальное страновое зеркало с предсказуемой инфраструктурой.После завершения `debootstrap` в `/mnt` находится работоспособная, но минимальная система. Она ещё не готова к загрузке: нет загрузчика, нет initramfs с поддержкой LUKS, нет конфигурации сети, нет пользователей. Все эти шаги выполняются позже, но уже внутри chroot-окружения, где `apt`, `systemd` и PAM работают так же, как в обычной системе.

Для входа в `chroot` необходимо смонтировать системные директории. Без них `apt` не сможет разрешать имена пакетов (нужен `/proc`), `systemd` не сможет создавать cgroups (нужен `/sys`), а PAM не сможет проверить учётные записи (нужен `/dev`). Порядок монтирования значения не имеет, но все пять директорий должны быть доступны до запуска `chroot`.

```bash
sudo mount --bind /dev     /mnt/dev
sudo mount --bind /dev/pts /mnt/dev/pts
sudo mount --bind /proc    /mnt/proc
sudo mount --bind /sys     /mnt/sys
sudo mount --bind /run     /mnt/run
sudo chroot /mnt /bin/bash
```

1. `/dev` и `/dev/pts` обеспечивают доступ к устройствам и псевдотерминалам. Без `/dev/pts` команды, которым нужен терминал (например, `passwd` или интерактивные части `apt`), будут падать с ошибкой «cannot open /dev/tty».
2. `/proc` нужен для работы `apt` (он читает `/proc/mounts` и `/proc/self/status`), для `systemd` (он использует `/proc/1` для определения PID 1) и для многих утилит, которые проверяют состояние ядра.
3. `/sys` нужен для `systemd` (cgroups), для `udev` и для инструментов, которые читают информацию об оборудовании.
4. `/run` — самый часто забываемый: без него `systemctl` в chroot не сможет связаться с systemd (если планируется что-то запускать), а `apt` будет ругаться на отсутствующий `/run/lock`. В Debian/Ubuntu это классическая ошибка при сборке через `debootstrap`, и она проявляется не сразу, а на этапе установки пакетов, когда `apt` пытается создать lock-файл.

После `chroot` среда выглядит как обычная система: работают `apt`, `systemctl` (в ограниченном режиме, без активного systemd), `passwd`, `useradd`. Но визуально оболочка никак не отличает себя от Live-среды: приглашение остаётся таким же, как до входа в chroot, и легко забыть, в каком окружении выполняется команда. Временная перезапись `PS1` устраняет эту неоднозначность:

```bash
# Внутри chroot: пометить приглашение на время текущей сессии
export PS1='\[\e[1;31m\][chroot]\[\e[0m\] \u@\h:\w\$ '
```

Команда меняет приглашение только в текущей оболочке. Маркер `[chroot]` имеет смысл только в сборочной сессии и не должен переживать первую загрузку.

Формат строки:

- `\[\e[1;31m\][chroot]\[\e[0m\]` — префикс `[chroot]` красным цветом. Красный выбран как сигнал «внимание, другое окружение»; `\[...\]` обязательны для корректной работы `readline` (без них `bash` неверно считает длину строки и ломает редактирование и историю).
- `\u@\h` — пользователь и hostname. Hostname внутри chroot остаётся тем же, что у Live-среды (chroot не меняет его автоматически), но префикс `[chroot]` снимает неоднозначность.
- `\w` — текущий рабочий каталог.
- `\$` — `#` для root, `$` для обычного пользователя.

Переменная экспортируется, поэтому дочерние `bash`-процессы, запущенные из текущей оболочки, наследуют её и тоже показывают маркер. Если оболочка закрыта и `chroot` выполнен заново, `export PS1=...` повторяется — это небольшая цена за то, что маркер гарантированно не остаётся в целевой системе. При выходе из chroot (`exit`) приглашение родительской оболочки возвращается к исходному виду автоматически, потому что `PS1` менялся только в дочернем процессе.

## 📦 Этап 3: Настройка APT и установка пакетов

Этап выполняется внутри `chroot` и определяет, какие пакеты попадут в целевую систему и с какими правилами они будут устанавливаться и обновляться. APT — единственный менеджер пакетов на станции; Snap заблокирован, сторонние PPA не используются, все компоненты берутся из официального архива Ubuntu. Это означает, что от корректной настройки APT зависит воспроизводимость всей сборки: один и тот же набор источников, одна и та же политика версий и одни и те же правила разрешения зависимостей дают одинаковый результат при каждом прогоне.

Этап состоит из трёх шагов. Первый — настройка источников в формате DEB822 с HTTPS и решением проблемы «курицы и яйца» для TLS: `debootstrap` не ставит корневые сертификаты, поэтому HTTPS-репозиторий до установки `ca-certificates` не работает. Второй — блокировка Snap через pinning: запрет оформляется до того, как пакет попадёт в дерево зависимостей, иначе `snapd` может приехать транзитивно с каким-нибудь метапакетом. Третий — базовая политика APT: минимализм, отсутствие интерактивных вопросов, экономия трафика и автоочистка сирот. Все три шага независимы, но порядок важен: источники настраиваются до политики, а политика — до установки пакетов.

### 🗂️ Этап 3.1: Источники APT в формате DEB822 (HTTPS + официальное зеркало)


Исторический формат APT — одна строка на репозиторий:

```
deb http://archive.ubuntu.com/ubuntu resolute main restricted universe multiverse
deb http://archive.ubuntu.com/ubuntu resolute-updates main restricted universe multiverse
deb http://archive.ubuntu.com/ubuntu resolute-security main restricted universe multiverse
```

У него три практических недостатка.

**Повторение.** Каждый suite — отдельная строка, URI и компоненты дублируются. Переход на другое зеркало — правка всех строк. Если строк десять (а с `deb-src` и дополнительными репозиториями их легко становится больше), забыть одну — обычное дело, и `apt update` начинает молча использовать старый источник для части suites.

**Нет структуры для метаданных.** `Signed-By`, `Architectures`, `Enabled: no` нельзя привязать к конкретному репозиторию — только глобально через `apt.conf`. Это значит, что ключ проверки подписи действует на все источники сразу, и добавление стороннего репозитория (например, Mozilla APT для Firefox) вынуждает либо доверять его ключам всё, либо городить костыли через `apt.conf.d` с переопределениями.

**Хрупкость парсинга.** Пробелы, комментарии, продолжения строк — всё это регулярки, которые легко сломать. Одна лишняя кавычка или перенос строки не в том месте — и APT молча игнорирует источник, а `apt update` завершается успешно, но без ожидаемых пакетов.

**DEB822** (`.sources`-файлы, RFC822-подобный формат `Ключ: Значение`) решает все три проблемы.

- **Один блок = один репозиторий** со всеми свойствами. Все поля относятся к этому блоку и только к нему.
- **`Suites:` принимает список** — один блок покрывает `resolute`, `resolute-updates` и `resolute-security`. Переход на другое зеркало — правка одной строки `URIs:`.
- **`Signed-By:`** — ключ проверки привязан **к конкретному источнику**, а не глобально. Это элемент безопасности: если позже будет добавлен сторонний репозиторий (Mozilla APT для Firefox), он не сможет подписаться ключом Ubuntu, и подмена пакетов между репозиториями становится невозможной.
- **`Enabled: no`** — можно временно отключить источник, не удаляя файл. Полезно при отладке: источник возвращается одной правкой, а не восстановлением из истории.

С Ubuntu 24.04 DEB822 — **рекомендуемый формат по умолчанию**, старый `sources.list` поддерживается только для совместимости. В 26.04 это норма, и `debootstrap` для `resolute` уже создаёт `.sources`-файл, а не `sources.list`.

> [!danger] Проблема «курицы и яйца»: сначала ca-certificates
> Настройка репозитория на HTTPS — правильный выбор, но `debootstrap --variant=minbase` **не устанавливает корневые сертификаты** — TLS-соединение не с чем проверить.
> Решение простое: `debootstrap` уже создал дефолтный `sources.list` (или `.sources`-файл), указывающий на **HTTP**-зеркало.
> Этого достаточно, чтобы поставить сертификаты штатным `apt` — без ручного `dpkg -i` и без временного отката схемы.
>
> ```bash
> apt update && apt install --no-install-recommends -y ca-certificates openssl
> ```
>
> После этого TLS работает, и можно использовать источник на HTTPS. Порядок именно такой: сначала HTTP, потом установка сертификатов, потом переключение на HTTPS.
> Обратный порядок даёт ошибку на первом же `apt update`.

> [!question] Выбор зеркала для Ubuntu
> В Российской Федерации используется страновое зеркало Ubuntu — `ru.archive.ubuntu.com`.
> Зеркало Яндекса исторически имело проблемы с цепочкой сертификатов и известно ложными предупреждениями `Missing Signed-By` при работе по HTTPS.
> Официальное российское зеркало `ru.archive.ubuntu.com` лишено этих особенностей и использует стандартную инфраструктуру Canonical.

```bash
rm -f /etc/apt/sources.list
cat > /etc/apt/sources.list.d/ubuntu.sources <<'EOF'
Types: deb
URIs: https://ru.archive.ubuntu.com/ubuntu/
Suites: resolute resolute-updates resolute-security
Components: main restricted universe multiverse
Signed-By: /usr/share/keyrings/ubuntu-archive-keyring.gpg
EOF
```

Удаление `/etc/apt/sources.list` перед созданием `.sources`-файла — не косметика, а необходимость. Если оставить оба файла, APT прочитает их оба, и один и тот же репозиторий будет фигурировать дважды: сначала по HTTP из `sources.list`, потом по HTTPS из `ubuntu.sources`. Это приводит к дублированию записей в `apt-cache policy` и к неочевидному поведению при выборе версии пакета.

| Поле | Значение | Почему так |
| :--- | :--- | :--- |
| `Types: deb` | Бинарные пакеты (не `deb-src`) | Исходники не нужны для эксплуатации. При необходимости (пересборка пакета с патчем) добавляется `Types: deb deb-src` для конкретного репозитория. |
| `URIs:` | `https://ru.archive.ubuntu.com/ubuntu/` | Официальное страновое зеркало с поддержкой HTTPS. Не зависит от особенностей сертификатной цепочки Яндекса. |
| `Suites:` | `resolute resolute-updates resolute-security` | **`resolute`** — базовый релиз (заморожен, security туда не попадает). **`resolute-updates`** — стабильные багфиксы. **`resolute-security`** — только security-патчи, приоритетный канал. **`resolute-backports`** сознательно не включён: backports — новые версии из будущего релиза, лишний риск для hardened-станции. |
| `Components:` | `main restricted universe multiverse` | **`main`** — свободное ПО с поддержкой Canonical. **`restricted`** — проприетарные драйверы. **`universe`** — свободное сообщества. **`multiverse`** — несвободное. Все четыре нужны. |
| `Signed-By:` | Путь к ключу | Зеркала подписывают пакеты оригинальными ключами Canonical — тот же ключ, что у `archive.ubuntu.com`. |

Три suites — не случайный набор. `resolute` фиксирует базовый релиз: он заморожен после выхода, security-патчи туда не попадают, и обновления из него приходят только при пересборке пакета в рамках point release. `resolute-updates` — стабильные багфиксы, которые проходят через процесс Canonical и не меняют поведение пакета без причины. `resolute-security` — приоритетный канал, куда попадают только security-патчи и куда APT обращается в первую очередь. Пропуск любого из трёх означает либо отсутствие обновлений безопасности, либо отсутствие исправлений ошибок, либо невозможность получить базовую версию пакета.

`resolute-proposed` и `resolute-backports` сознательно не включены. `proposed` — staging-канал, куда попадают обновления до стабилизации; его подключение означает, что система получает пакеты, которые ещё не прошли полный цикл тестирования, и ломается в самый неподходящий момент. `backports` — новые версии из будущего релиза; для hardened-станции, которая собирается по фиксированному манифесту, это лишний риск несовместимости без выгоды.

> [!info] Про настройку репозитория Ubuntu
> - **`deb-src`** — исходники не нужны. При необходимости (пересборка пакета с патчем) — отдельный `.sources`-файл.
> - **`resolute-proposed`** — staging-канал, куда попадают обновления до стабилизации. **Никогда не включается на рабочей станции** — сломает систему в самый неподходящий момент.
> - **`resolute-backports`** — новые версии из будущего релиза. Лишний риск несовместимости для hardened-станции.

Дополнительно фиксируется политика проверки в отдельном файле — это не меняет поведение по умолчанию (проверка включена), но делает намерение явным и защищает от случайного отключения в будущем:

```bash
cat > /etc/apt/apt.conf.d/99-https-verify <<'EOF'
Acquire::https::Verify-Peer "true";
Acquire::https::Verify-Host "true";
EOF
```

| Опция | Что проверяет |
| :--- | :--- |
| `Acquire::https::Verify-Peer "true"` | Проверяет сертификат сервера против доверенных корневых сертификатов (`/etc/ssl/certs`). |
| `Acquire::https::Verify-Host "true"` | Проверяет, что Common Name (CN) или Subject Alternative Name (SAN) сертификата соответствует запрошенному хосту (`ru.archive.ubuntu.com`). |

Обе опции по умолчанию **уже `true`** — файл нужен как документация и страховка от случайного `false` в других конфигах. `Verify-Peer` защищает от подмены сертификата самоподписанным, `Verify-Host` — от подмены сервера при валидном сертификате другого хоста. Отключение любой из них означает, что TLS-соединение проверяет только шифрование, но не аутентичность сервера, и MITM-атака на канал обновлений становится тривиальной.

### 🚫 Этап 3.2: Блокировка Snap через pinning

Этот подэтап определяет, какие пакеты APT имеет право устанавливать, и не даёт Snap просочиться в систему. Snap в 26.04 — это второй менеджер пакетов со своим демоном, автообновлением, loopback-устройствами, изолированными окружениями и привязкой к Canonical Store. Для минималистичной, воспроизводимой станции это антипаттерн: ещё один источник обновлений, ещё одна поверхность атаки и ещё одна точка, где поведение системы перестаёт быть предсказуемым. Блокировать его нужно на уровне APT — чтобы запрет работал до того, как пакет попадёт в дерево зависимостей.

> [!question] Snap как источник недетерминизма
> Snap-демон ставит свои обновления в обход `apt`, в фоновом режиме, по расписанию Canonical.
> Это значит, что на станции появляется канал обновлений, который не контролируется ни через `unattended-upgrades`, ни через собственные пиннинги, ни через фиксацию версий.
> Для станции, которая собирается по фиксированному манифесту, это ломает саму идею воспроизводимости: два прогона сборки в разное время дают разное состояние.

Для блокировки используется механизм приоритетов — pinning. Каждому пакету из каждого репозитория APT присваивает приоритет, по умолчанию 500. Pinning позволяет понизить приоритет (пакет не будет выбран), повысить его (будет выбран вместо других) или **запретить установку** отрицательным приоритетом. Механизм работает на уровне выбора версии: APT видит все доступные версии пакета из всех источников, применяет к каждой приоритет, и выбирает версию с максимальным приоритетом. Если максимальный приоритет отрицательный, версия не выбирается вообще.

Шкала приоритетов:

| Приоритет | Поведение |
| :--- | :--- |
| `1001+` | Установить даже при downgrade (опасно) |
| `990` | Установить, даже если это downgrade |
| `500` (default) | Обычная установка |
| `100` | Установить, только если нет другой версии |
| `0` | Не ставить автоматически, но можно явно |
| **`-1` и ниже** | **Никогда не устанавливать, даже явно** |
| `-10` | То же, но с запасом (старые версии APT трактовали `-1` нестрого) |

Запись `Pin: release a=*` означает, что пин применяется **ко всем версиям** пакета из всех репозиториев: `a=*` — любой archive. Это важно: `snapd` присутствует в `main` и `universe`, а со временем может появиться в сторонних репозиториях. Пин по wildcard-маске закрывает все эти каналы сразу. Если пин привязать к конкретному archive (`a=resolute`), `snapd` из `resolute-updates` или стороннего репозитория обойдёт запрет. Запрет оформляется так:

```bash
cat > /etc/apt/preferences.d/nosnap.pref <<'EOF'
Package: snapd
Pin: release a=*
Pin-Priority: -10
EOF
```

| Поле | Значение | Почему так |
| :--- | :--- | :--- |
| `Package: snapd` | Единственный пакет, к которому применяется пин | `snapd` — демон Snap. Остальные snap-пакеты (`snap-confine`, `snap-tool`) ставятся только как его зависимости, поэтому блокировки одного `snapd` достаточно. |
| `Pin: release a=*` | Любой archive | `a=*` — wildcard по полю archive. Подходит ко всем версиям из всех репозиториев: `main`, `restricted`, `universe`, будущих сторонних. |
| `Pin-Priority: -10` | Запрет | `-10` вместо `-1`: старые версии APT трактовали `-1` нестрого, а `-10` гарантирует отказ даже при явной команде `apt install snapd`. |

Проверка применения:

```bash
apt-cache policy snapd
```

В выводе `Installed:` и `Candidate:` должны показывать `(none)`, а версия пакета — приоритет `-10`. При попытке `apt install snapd` APT ответит `Package 'snapd' has no installation candidate` — это и есть ожидаемое поведение. Если позже понадобится поставить `snapd` осознанно (например, для тестирования), придётся временно повысить приоритет — то есть принять явное решение, а не получить Snap «по умолчанию».

Блокировка одного `snapd` достаточна, потому что все остальные snap-компоненты — его зависимости. `snap-confine` (утилита изоляции), `snap-tool` (обёртка над `snapd`), `ubuntu-core-launcher` (старое имя `snap-confine`) не устанавливаются сами по себе: они появляются только как `Depends` от `snapd`. Если `snapd` запрещён, запрещено и всё дерево. Обратное неверно: блокировка `snap-confine` не помешает установке `snapd`, который притащит `snap-confine` заново.

### 🧭 Этап 3.3: Базовая политика APT

Файл базовой политики фиксирует правила APT на станции: минимум лишних пакетов, отсутствие интерактивных вопросов при обновлении, экономия трафика и автоочистка сирот. Без такого файла поведение APT зависит от того, помнит ли администратор флаг `--no-install-recommends` и `-y` в каждой команде; с файлом — становится свойством системы, а не привычкой человека. Это важно в том числе для `unattended-upgrades`, который работает без администратора и следует глобальной политике, а не отдельным флагам. Создаётся файл так:

```bash
cat > /etc/apt/apt.conf.d/00-base-policy <<'EOF'
APT::Install-Recommends "false";
APT::Install-Suggests "false";
Dpkg::Options { "--force-confdef"; "--force-confold"; };
Acquire::Languages "none";
APT::Get::AutomaticRemove "true";
EOF
```

Файлы в каталоге `/etc/apt/apt.conf.d/` читаются в лексикографическом порядке. Префикс `00-` гарантирует, что этот файл будет прочитан **раньше** остальных. Поэтому его значения становятся базой, которую другие файлы при необходимости могут переопределить. Без префикса файл мог бы быть прочитан после `99-https-verify` или других, и его значения не применились бы к первым командам.

| Параметр | Что делает | Почему так |
| :--- | :--- | :--- |
| `APT::Install-Recommends "false"` | Не ставит Recommended-пакеты | Recommended — «обычно нужно вместе с этим». Ставить их — значит тащить в систему десятки пакетов «на всякий случай». Осознанный минимум лучше, но требует ручного контроля критичных Recommended. |
| `APT::Install-Suggests "false"` | Не ставит Suggested-пакеты | Suggested — «может пригодиться». Почти всегда это мусор вроде `ghostscript`, `fonts-urw-base35`, `python3-tk`. Для минималистичной системы `false` — стандарт. |
| `Dpkg::Options { "--force-confdef"; "--force-confold"; }` | Конфликты конфигов — без интерактивных вопросов | В скриптовой сборке `dpkg` не должен спрашивать «оставить старый конфиг?». `confold` (а не `confnew`) — потому что правки важнее новых дефолтов из пакета. |
| `Acquire::Languages "none"` | Не скачивает переводы описаний | По умолчанию APT качает `Translation-en`, `Translation-ru` и другие — десятки МБ при каждом `apt update`. `none` экономит трафик; английские описания для DevOps-станции достаточны. |
| `APT::Get::AutomaticRemove "true"` | Удаляет сирот при install/upgrade | Меньше мусора, меньше поверхность атаки: старые библиотеки с CVE не висят «на всякий случай». Риск — можно потерять пакет, помеченный `auto` вручную. |

Порядок `--force-confdef` перед `--force-confold` важен. `confdef` обрабатывает случаи, когда конфигурационный файл не менялся с момента установки пакета — тогда `dpkg` берёт новую версию без вопросов. `confold` обрабатывает случаи, когда файл менялся — тогда `dpkg` оставляет локальную версию. Если поменять их местами, `dpkg` будет предпочитать новую версию даже при наличии локальных правок, и настройки потеряются при обновлении.

> [!danger] Обратная сторона отключения Recommended
> Recommended — это не «совсем необязательные» пакеты, а «нужные в 90% случаев». Пример: `libpwquality1` рекомендует `cracklib-runtime` — без него ломается смена пароля через `passwd`.
> Поэтому критичные Recommended ставятся **явно, вручную**: `cracklib-runtime`, `publicsuffix`, `mesa-utils`, `xclip` и другие.
> Если пакет нужен, но не является жёсткой зависимостью, его отсутствие проявится в первом же прогоне сценария — это нормальная цена за минимализм.

> [!warning] Обратная сторона `confold`
> `confold` оставляет старый конфиг при конфликте, но **не добавляет** в него новые опции, появившиеся в новой версии пакета.
> Раз в полгода полезно сверять конфликтные файлы:
>
> ```bash
> dpkg-query -W -f='${Conffiles}\n' <package>
> ```
>
> Команда покажет все conffiles пакета; для каждого можно сравнить с версией из пакета через `apt-get download` и `dpkg-deb -x`.

> [!tip] Сохранение пакета от автоудаления
> `AutomaticRemove` удаляет всё, что помечено как `auto` и больше никому не нужно.
> Если пакет ставился как зависимость, а потом стал нужен сам по себе — он помечается как ручной, и автоудаление его не тронет:
>
> ```bash
> apt-mark manual <pkg>
> ```
>
> Обратная операция — `apt-mark auto <pkg>`: пакет снова становится кандидатом на автоудаление.

В итоге этот файл делает три вещи. Он фиксирует минимализм (Recommended и Suggested отключены), убирает интерактивность (`confold` вместо вопросов `dpkg`), экономит трафик (`Languages "none"`) и автоматически поддерживает чистоту (`AutomaticRemove`). Цена — ручной контроль критичных Recommended и периодическая сверка conffiles. Это осознанный компромисс: предсказуемость и воспроизводимость важнее удобства «поставилось само».

## ⚙️ Этап 4: Базовая конфигурация системы

Этот этап отвечает на вопрос «как система идентифицирует себя»: какое окружение получает пользователь, как настраивается клавиатура, как поднимается сеть, какие параметры ядра применяются, какие файловые системы и опции монтируются при загрузке, как управляется память и выдаются привилегии. Подразделы независимы друг от друга: сетевой стек можно менять, не трогая fstab, и наоборот.

Каждый подраздел фиксирует одно решение в одном файле или наборе файлов. Это осознанный принцип: конфигурация, размазанная по десятку мест, не поддаётся версионированию и плохо диагностируется. Один файл — один слой ответственности; при отладке всегда ясно, где искать причину.

### 🌍 Этап 4.1: Переменные окружения

Первый подраздел задаёт базовый контракт между системой и графическими приложениями: в какой сессии они работают (Wayland), какой у них backend для Qt и Electron, как они должны вести себя с HiDPI, и какой `PATH` им доступен. Всё это фиксируется в одном системном файле, который PAM читает при логине.

`debootstrap` уже создал `/etc/environment` с дефолтным PATH из Ubuntu-образа, который включает `/snap/bin` и `/usr/games`. Для этой станции оба пути нежелательны: Snap заблокирован через pinning (Этап 3.2), а игр на DevOps/NetOps-станции нет. Поэтому файл перезаписывается целиком — с чистым PATH и Wayland-переменными:

```bash
cat > /etc/environment <<'EOF'
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
XDG_SESSION_TYPE=wayland
XDG_CURRENT_DESKTOP=qtile
QT_QPA_PLATFORM="wayland;xcb"
MOZ_ENABLE_WAYLAND=1
ELECTRON_OZONE_PLATFORM_HINT=auto
EOF
```

`/etc/environment` — **системный** файл переменных окружения, который PAM читает при логине (`pam_env.so`). Он применяется **до** запуска пользовательской сессии, поэтому переменные видны композитору, Qtile и всем приложениям сессии.

| Переменная | Значение | Почему именно так |
| :--- | :--- | :--- |
| `PATH` | `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` | `local/*` раньше системных — стандартный FHS-принцип: локально установленные бинарники переопределяют системные. `/sbin` после `bin` — стандарт Debian: обычные утилиты раньше root-инструментов. `/snap/bin` убран (Snap заблокирован), `/usr/games` убран (нет игр). |
| `XDG_SESSION_TYPE=wayland` | Тип сессии — Wayland | Сообщает приложениям (Firefox, Chromium, Qt, GTK), что они в Wayland-сессии. Без неё некоторые попытаются подключиться к `$DISPLAY` (X11), которого может не быть. |
| `XDG_CURRENT_DESKTOP=qtile` | Имя текущего DE/WM | `xdg-desktop-portal` выбирает backend по этой переменной; GTK-приложения меняют тему; Electron выбирает, какие диалоги показывать. |
| `QT_QPA_PLATFORM="wayland;xcb"` | Backend для Qt | `wayland` — нативный Wayland (правильные HiDPI, фракционный скейлинг). `xcb` — fallback на X11 через XWayland. Точка с запятой задаёт приоритет. |
| `MOZ_ENABLE_WAYLAND=1` | Firefox → Wayland | Firefox до сих пор может выбирать X11-backend. Переменная явно говорит «используй Wayland». |
| `ELECTRON_OZONE_PLATFORM_HINT=auto` | Electron → Wayland (авто) | Electron-приложения (VS Code, Slack, Discord) исторически шли через XWayland. `auto` означает «попробуй Wayland, если не получилось — X11». |

> [!question] Почему в `/etc/environment`, а не в `~/.profile` или конфиге Qtile?
> Во-первых, порядок применения: файл читается PAM **до** запуска сессии, поэтому переменные видны уже композитору и его потомкам. `~/.profile` появится только в шелле после логина.
> Во-вторых, системный уровень: для воспроизводимости это правильно — все пользователи получают одинаково настроенную Wayland-сессию.
> В-третьих, независимость от shell: `~/.profile` читается только login-shell'ом. Если Qtile запускается через `exec` из display manager'а, `~/.profile` может вообще не прочитаться.
> `/etc/environment` работает гарантированно.
> В-четвёртых, `pam_env` выставляет `PATH` для приложений, запущенных не через shell (`.desktop`-файлы, systemd user units).
> Без явного `PATH` в `/etc/environment` они могут получить неполный PATH.

> [!danger] `>` для первого блока, `>>` для последующих
> Первый `cat >` создаёт файл с нуля (PATH + Wayland-переменные). Все последующие — `cat >>`, чтобы дописывать тему, раскладку и т.д.
> Если случайно использовать `>` во втором блоке — PATH и Wayland-переменные будут затёрты.

### ⌨️ Этап 4.2: Раскладка клавиатуры

Раскладка клавиатуры — это не уровень Qtile и не уровень X11. В Wayland-сессии композитор (Qtile) отвечает за **низкоуровневую** передачу скан-кодов, но **карта раскладки** (keymap) настраивается отдельно — через переменные окружения XKB, которые читают все приложения, поддерживающие этот протокол. Сложные методы ввода (IME) здесь не требуются: для пары us/ru достаточно уровня XKB.

Настройки добавляются в `/etc/environment`:

```bash
cat >> /etc/environment <<'EOF'
XKB_DEFAULT_LAYOUT=us,ru
XKB_DEFAULT_OPTIONS=grp:caps_toggle,caps:none
EOF
```

`XKB_DEFAULT_LAYOUT` — список раскладок через запятую (порядок важен: `us` первая, `ru` вторая). `XKB_DEFAULT_OPTIONS` — список опций через запятую. Здесь используются две:

- **`grp:caps_toggle`** — CapsLock переключает группу раскладок (us ↔ ru). Нажатие CapsLock меняет язык ввода.
- **`caps:none`** — отключает штатное поведение CapsLock (фиксацию верхнего регистра). Это нужно, потому что `grp:caps_toggle` уже «забирает» CapsLock себе; без `caps:none` CapsLock одновременно переключал бы раскладку **и** включал Caps Lock, что приводило бы к неожиданному поведению (например, при переключении на русский получались бы «ЗАГЛАВНЫЕ» буквы).

Другие популярные варианты для `grp:` — `grp:alt_shift_toggle` (Alt+Shift), `grp:win_space_toggle` (Win+Space). При выборе Alt+Shift `grp:caps_toggle` заменяется на `grp:alt_shift_toggle`, а `caps:none` убирается (CapsLock возвращается к штатному поведению).

> [!info] Если Qtile игнорирует `XKB_DEFAULT_LAYOUT`
> Некоторые версии Qtile на Wayland считывают layout из своего конфига, а не из переменных окружения. В этом случае в `~/.config/qtile/config.py` добавляется:
> ```python
> from libqtile.backend.wayland import InputConfig
> wl_input_rules = {
>     "type:keyboard": InputConfig(
>         kb_layout="us,ru",
>         kb_options="grp:caps_toggle,caps:none",
>     ),
> }
> ```
> Переменные из `/etc/environment` при этом остаются как fallback для приложений, которые не читают конфиг Qtile.
> Список опций должен совпадать в обоих местах — иначе поведение будет разным для Qtile-нативных окон и для XWayland-приложений.

Текстовая консоль (виртуальные терминалы `tty1`–`tty6`, а также экран ввода пароля LUKS на раннем этапе загрузки) не читает `/etc/environment`. Она использует собственный конфигурационный файл `/etc/default/keyboard`, который обрабатывается пакетами `console-setup` и `kbd` при загрузке. Конфигурация зеркалит настройки XKB, чтобы поведение было одинаковым и в графике, и в консоли:

```bash
cat > /etc/default/keyboard <<'EOF'
XKBMODEL="pc105"
XKBLAYOUT="us,ru"
XKBOPTIONS="grp:caps_toggle,caps:none"
BACKSPACE="guess"
EOF
```

`XKBMODEL="pc105"` указывает на стандартную модель клавиатуры с 105 клавишами, `XKBLAYOUT` и `XKBOPTIONS` повторяют настройки Wayland, а `BACKSPACE="guess"` автоматически определяет поведение клавиши Backspace (важно для некоторых USB-клавиатур и старых PS/2). После создания файла настройки применяются к текущей среде утилитой `setupcon` (при загрузке они применятся автоматически):

```bash
setupcon
```

> [!warning] Пароль LUKS вводится в консольной раскладке
> На этапе разблокировки LUKS графическая сессия ещё не запущена, и ввод пароля происходит в консоли (TTY), которая использует `/etc/default/keyboard`.
> Если пароль LUKS содержит символы, расположение которых отличается в `us` и `ru` (например, `@`, `#`, `$`), убедитесь, что вы вводите его в правильной раскладке.
> По умолчанию загружается **первая** раскладка из списка (`us`), поэтому пароль LUKS лучше задавать в латинской раскладке.

### 🌐 Этап 4.3: Сетевой стек без NetworkManager

Подраздел заменяет NetworkManager детерминированной связкой `systemd-networkd` + `wpa_supplicant` + `systemd-resolved`. Конфигурация — это файлы в `/etc/systemd/network/` и `/etc/wpa_supplicant/`, которые можно версионировать и которые не меняются «самим собой».

Ключевой момент, который нужно усвоить сразу: **`networkctl` не умеет подключаться к Wi-Fi**. Это инструмент мониторинга и управления линками для `systemd-networkd`. Сам Wi-Fi-аутентификацией занимается `wpa_supplicant`, а интерактивным клиентом к нему служит `wpa_cli`.

| Слой | Компонент | Что делает |
| :--- | :--- | :--- |
| Аутентификация Wi-Fi | `wpa_supplicant` | Ассоциация с точкой доступа, WPA2/WPA3, roaming. |
| IP-адресация | `systemd-networkd` | DHCP-клиент, маршруты, линки. |
| DNS | `systemd-resolved` | Stub-resolver на `127.0.0.53`, кэш, DNSSEC. |
| Мониторинг | `networkctl` | `networkctl status`, `networkctl list`. |
| Интерактивное подключение | `wpa_cli` | `scan`, `add_network`, `set_network`, `enable_network`. |

Сначала включаются службы и настраивается симлинк для резолвера:

```bash
systemctl enable systemd-networkd
systemctl enable systemd-resolved
systemctl enable wpa_supplicant@wlp3s0.service
ln -sf /run/systemd/resolve/stub-resolv.conf /etc/resolv.conf
```

Имя интерфейса `wlp3s0` взято из инвентаризации Этапа 0. При другом Wi-Fi-адаптере имя будет отличаться; проверка выполняется через `networkctl list` или `ip -br link` (пакет `iproute2` уже установлен на Этапе 3.4).

Конфигурация `systemd-networkd` — два файла: Wi-Fi и Ethernet. Ethernet-файл нужен на случай подключения кабеля.

```bash
# Wi-Fi (wlp3s0)
cat > /etc/systemd/network/25-wireless.network <<'EOF'
[Match]
Name=wlp3s0

[Network]
DHCP=yes

[DHCPv4]
RouteMetric=600
EOF

# Ethernet (eno1) — с более высоким приоритетом
cat > /etc/systemd/network/20-wired.network <<'EOF'
[Match]
Name=eno1

[Network]
DHCP=yes

[DHCPv4]
RouteMetric=100
EOF
```

`RouteMetric=100` для Ethernet и `600` для Wi-Fi означает, что при одновременном подключении трафик пойдёт через кабель.

Конфигурация `wpa_supplicant` лежит в файле, имя которого соответствует имени сервиса: `wpa_supplicant@wlp3s0.service` читает `/etc/wpa_supplicant/wpa_supplicant-wlp3s0.conf`:

```bash
cat > /etc/wpa_supplicant/wpa_supplicant-wlp3s0.conf <<'EOF'
ctrl_interface=DIR=/var/run/wpa_supplicant GROUP=netdev
update_config=1
country=RU

network={
    ssid="<SSID_СЕТИ>"
    psk="<ПАРОЛЬ_СЕТИ>"
    key_mgmt=WPA-PSK
}
EOF
chmod 600 /etc/wpa_supplicant/wpa_supplicant-wlp3s0.conf
```

Права `600` обязательны: файл содержит PSK в открытом виде, и читать его должен только root. `ctrl_interface` с `GROUP=netdev` разрешает `wpa_cli` управлять `wpa_supplicant` членам группы `netdev`.

> [!tip] Альтернатива — не хранить пароль в открытом виде
> ```bash
> wpa_passphrase "<SSID_СЕТИ>" "<ПАРОЛЬ_СЕТИ>" >> /etc/wpa_supplicant/wpa_supplicant-wlp3s0.conf
> ```
> Утилита создаст блок `network={ ssid=... #psk="..." psk=<hex> }`, где пароль в открытом виде закомментирован, а рабочий `psk` хранится в hex.
> Комментарий с паролем можно удалить вручную — после этого файл содержит только hex-PSK.

> [!warning] Диагностика при сбое
> `journalctl -u systemd-networkd -u wpa_supplicant@wlp3s0 -b` показывает, на каком этапе произошёл сбой.
> `wpa_cli -i wlp3s0 status` — состояние ассоциации (`wpa_state=COMPLETED` означает успех).
> `networkctl status` — что видит `systemd-networkd` со своей стороны.

### 🚀 Этап 4.4: Сетевой sysctl-тюнинг (BBR, fq, low-latency)

Для стационарного ПК, особенно при игре и работе с сетевыми сервисами, стандартный CUBIC + `fq_codel` — не оптимальный выбор. TCP BBR даёт заметно меньшую задержку и лучшую пропускную способность на потерях, а `fq` (fair queue) — правильный qdisc для BBR. Все параметры фиксируются в drop-in файле, который читается при загрузке.

Drop-in создаётся в `/etc/sysctl.d/`:

```bash
cat > /etc/sysctl.d/99-network-performance.conf <<'EOF'
# BBR congestion control + fair queue
net.core.default_qdisc = fq
net.ipv4.tcp_congestion_control = bbr

# Low-latency: не буферизовать «лишние» байты в сокете
net.ipv4.tcp_notsent_lowat = 16384

# Буферы сокетов (для стационарного ПК с 32+ ГБ RAM — разумный компромисс)
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# Быстрое переиспользование TIME_WAIT (для активного серфинга/игр)
net.ipv4.tcp_fin_timeout = 15
net.ipv4.tcp_tw_reuse = 1

# Очередь на входящие соединения
net.core.somaxconn = 4096
net.ipv4.tcp_max_syn_backlog = 8192
EOF
```

> [!info] Почему именно эти параметры
> `net.core.default_qdisc = fq` и `net.ipv4.tcp_congestion_control = bbr` — базовая связка для BBR.
> `fq` даёт fair queueing, который BBR использует для оценки пропускной способности. Без `fq` BBR работает, но менее эффективно.
> `tcp_notsent_lowat = 16384` снижает задержку, не позволяя TCP-стеку держать в сокете больше 16 КБ непереданных данных. Полезно для интерактивных приложений (SSH, игры, HTTP).
> `tcp_tw_reuse = 1` позволяет переиспользовать сокеты в состоянии TIME_WAIT для новых исходящих соединений.
> Безопасно на клиентской машине, заметно снижает задержку при активном серфинге.
> Буферы `rmem_max`/`wmem_max` на 16 МБ — разумный потолок для домашней сети; больше — только для 10G+ или BDP-тяжёлых каналов.

Применение и проверка:

```bash
sysctl --system
sysctl net.ipv4.tcp_congestion_control   # ожидаем bbr
sysctl net.core.default_qdisc            # ожидаем fq
```

> [!warning] Если `bbr` недоступен
> Проверка выполняется командой `sysctl net.ipv4.tcp_available_congestion_control`. Если `bbr` в списке нет, ядро собрано без него (маловероятно для Ubuntu 26.04, но возможно).
> В этом случае остаётся fallback: `net.core.default_qdisc = fq_codel`, `net.ipv4.tcp_congestion_control = cubic`.

> [!tip] Модуль `tcp_bbr`
> В некоторых ядрах `tcp_bbr` собран как модуль. Если `bbr` не появляется, `tcp_bbr` добавляется в `/etc/modules-load.d/bbr.conf`:
> ```bash
> echo tcp_bbr > /etc/modules-load.d/bbr.conf
> ```
> После этого нужна перезагрузка.

### 🗂️ Этап 4.5: fstab и crypttab — эталонные опции монтирования

Два файла задают идентичность дисковой подсистемы: `/etc/crypttab` описывает LUKS-контейнеры, которые нужно разблокировать при загрузке, `/etc/fstab` — что и куда монтировать и с какими опциями. Оба файла напрямую влияют на производительность и безопасность, поэтому опции подобраны осознанно, а не скопированы из `defaults`.

`crypttab` генерируется автоматически из UUID раздела. Основное решение здесь — опция `discard`, которая разрешает проброс TRIM-команд к SSD. Это нужно для сохранения производительности NVMe со временем: без TRIM контроллер SSD не знает, какие блоки свободны, и постепенно деградирует. Минус — небольшая утечка информации: по паттерну TRIM-запросов теоретически можно судить о том, какие блоки освободились. Для домашней станции это приемлемый компромисс.

```bash
LUKS_UUID=$(cryptsetup luksUUID /dev/nvme0n1p3)
cat > /etc/crypttab <<EOF
cryptroot UUID=${LUKS_UUID} none luks,discard
EOF
```

`fstab` собирается из UUID, которые выдаёт `blkid`. Ручная подстановка UUID чревата опечатками: одна неверная цифра — и система уходит в emergency mode при загрузке, а сообщение об ошибке не всегда указывает на конкретную строку. Поэтому генерация `fstab` выполняется скриптом, который сам собирает UUID с устройств, проверяет их наличие и уникальность, делает резервную копию текущего файла и записывает новый атомарно.

Скрипт рассчитан на имена устройств из этого документа (`/dev/vg0/*`, `/dev/nvme0n1p1`, `/dev/nvme0n1p2`). При другой разметке достаточно изменить ассоциативный массив `DEV` в начале.

```bash
cat > /usr/local/sbin/gen-fstab <<'SCRIPT'
#!/bin/bash
set -euo pipefail

# --- mapping: logical name -> block device ---
declare -A DEV=(
    [root]=/dev/vg0/root
    [boot]=/dev/nvme0n1p2
    [efi]=/dev/nvme0n1p1
    [home]=/dev/vg0/home
    [var_log]=/dev/vg0/var_log
    [libvirt]=/dev/vg0/libvirt
    [containers]=/dev/vg0/containers
)

command -v blkid >/dev/null || { echo "ERROR: blkid not found" >&2; exit 1; }

# --- collect UUIDs ---
declare -A UUID
for key in "${!DEV[@]}"; do
    dev="${DEV[$key]}"
    [ -b "$dev" ] || { echo "ERROR: $dev is not a block device" >&2; exit 1; }
    uuid=$(blkid -s UUID -o value "$dev" 2>/dev/null || true)
    [ -n "$uuid" ] || { echo "ERROR: $dev has no UUID (not formatted?)" >&2; exit 1; }
    UUID[$key]="$uuid"
done

# --- sanity: no duplicate UUIDs ---
declare -A seen
for key in "${!UUID[@]}"; do
    u="${UUID[$key]}"
    [ -n "${seen[$u]:-}" ] && { echo "ERROR: duplicate UUID $u for $key and ${seen[$u]}" >&2; exit 1; }
    seen[$u]="$key"
done

# --- backup existing fstab ---
if [ -e /etc/fstab ]; then
    cp -a /etc/fstab "/etc/fstab.bak.$(date +%Y%m%d-%H%M%S)"
fi

# --- atomic write ---
tmp=$(mktemp /etc/.fstab.new.XXXXXX)
trap 'rm -f "$tmp"' EXIT

line() {
    printf '%-42s %-24s %-7s %-49s %-6s %s\n' "$@"
}

{
    line "# <file system>" "<mount point>" "<type>" "<options>" "<dump>" "<pass>"
    line "UUID=${UUID[root]}"       "/"                   "xfs"   "defaults,noatime"                        "0" "1"
    line "UUID=${UUID[boot]}"       "/boot"               "ext4"  "defaults,noatime"                        "0" "2"
    line "UUID=${UUID[efi]}"        "/boot/efi"           "vfat"  "umask=0077,noatime"                      "0" "1"
    line "UUID=${UUID[home]}"       "/home"               "xfs"   "defaults,noatime"                        "0" "2"
    line "UUID=${UUID[var_log]}"    "/var/log"            "xfs"   "defaults,noatime"                        "0" "2"
    line "UUID=${UUID[libvirt]}"    "/var/lib/libvirt"    "xfs"   "defaults,noatime"                        "0" "2"
    line "UUID=${UUID[containers]}" "/var/lib/containers" "xfs"   "defaults,noatime"                        "0" "2"
    line "tmpfs"                    "/tmp"                "tmpfs" "defaults,nosuid,nodev,noatime,mode=1777" "0" "0"
} > "$tmp"

chmod 0644 "$tmp"
mv -f "$tmp" /etc/fstab
trap - EXIT

echo "=== /etc/fstab written ==="
cat /etc/fstab

# --- optional verification (util-linux) ---
if command -v findmnt >/dev/null; then
    echo "=== findmnt --verify ==="
    findmnt --verify || echo "WARN: findmnt --verify reported issues (see above)" >&2
fi
SCRIPT
chmod 0755 /usr/local/sbin/gen-fstab

/usr/local/sbin/gen-fstab
```

Скрипт выполняет шесть шагов. На первом собираются UUID всех устройств через `blkid -s UUID -o value`; для каждого проверяется, что устройство существует как блочное (`-b`) и что у него есть UUID, то есть оно отформатировано. Если хоть одно условие не выполнено, скрипт завершается с ошибкой, не трогая `fstab`: это защищает от ситуации, когда `fstab` уже перезаписан, а одно из устройств по какой-то причине не готово.

На втором шаге проверяется отсутствие дубликатов UUID. Сами UUID уникальны по спецификации, но если в массиве `DEV` один и тот же путь окажется под двумя ключами, скрипт это заметит. Это дешёвая проверка, которая ловит опечатки в конфигурации.

На третьем шаге создаётся резервная копия `/etc/fstab.bak.<дата>-<время>`. Если что-то пойдёт не так, файл всегда можно вернуть.

На четвёртом шаге новый `fstab` пишется в `mktemp /etc/.fstab.new.XXXXXX` на той же файловой системе, после чего `mv -f` атомарно подменяет `/etc/fstab`. При прерывании скрипта (Ctrl+C, обрыв SSH) `/etc/fstab` остаётся прежним, частично записанного файла не бывает. `trap` удаляет временный файл при любом выходе, кроме успешного.

На пятом шаге выводится готовый `fstab` для визуальной сверки.

На шестом шаге `findmnt --verify` (если доступен) проверяет, что все точки монтирования существуют и синтаксис корректен. Предупреждения `findmnt` не фатальны: он может ругаться на `tmpfs` или на отсутствие некоторых точек в момент проверки, но реальные проблемы (например, дублирующийся mount point) будут видны.

Опции монтирования подобраны осознанно, а не скопированы из `defaults`:

| Опция | Где применяется | Почему так |
| :--- | :--- | :--- |
| `noatime` | XFS, ext4 | Отключает обновление времени доступа при чтении файла. Для XFS по умолчанию используется `relatime`, который почти так же эффективен, но `noatime` полностью убирает лишние записи метаданных при чтении. Для десктопа это безопасно: программы, которым действительно нужен `atime` (например, `mutt`), используют `O_NOATIME` или явно включают его. |
| `noatime` на `/boot/efi` | vfat | ESP почти не читается после загрузки, но `noatime` убирает единственную причину для записи при чтении. |
| `umask=0077` на `/boot/efi` | vfat | Ограничивает доступ к ESP только root. Файлы внутри ESP не должны быть доступны обычным пользователям. |
| `mode=1777` на `/tmp` | tmpfs | Стандартные права для `/tmp`: все могут писать, но удалять — только владелец (sticky bit). `tmpfs` не сохраняет права при пересоздании, поэтому `mode=1777` нужно указать явно. |
| `nosuid,nodev` на `/tmp` | tmpfs | Запрещает SUID-бинарники и device-файлы в `/tmp`. Базовая мера для hardened-системы. |
| `async` на XFS | — | **Не добавляется.** `async` означает «игнорировать fsync», что даёт прирост скорости ценой потери данных при отключении питания. Для станции с LUKS и бэкапами это неоправданный риск. XFS и так агрессивно кэширует записи. |

Скрипт сохранён в `/usr/local/sbin/gen-fstab` и остаётся в системе. При изменении разметки (добавлении нового LVM-тома, замене диска) достаточно поправить массив `DEV` и перезапустить скрипт: `fstab` будет перегенерирован с актуальными UUID, а резервная копия предыдущей версии сохранится рядом.

> [!tip] Про `logbufs` и `logbsize`
> На XFS можно увеличить `logbufs=8` и `logbsize=256k` для лучшей производительности журнала при интенсивной записи (ВМ, контейнеры, сборки).
> Но это имеет смысл только при подтверждённой нагрузке.
> Начинается конфигурация с `defaults,noatime`; при обнаружении узкого места в журнале XFS (`xfs_info` и `iostat -x` покажут) опции добавляются в скрипт, и `fstab` перегенерируется:
> ```
> defaults,noatime,logbufs=8,logbsize=256k
> ```

### 💾 Этап 4.6: ZRAM (сжатый swap в RAM)

ZRAM создаёт блочное устройство в оперативной памяти, которое сжимает страницы. Это даёт «swap», который в разы быстрее диска и не изнашивает SSD. Для станции с 32+ ГБ RAM это скорее страховка от редких пиков, чем необходимость, но настроить стоит: цена нулевая, а выигрыш при неожиданном пике потребления памяти заметный.

```bash
cat > /etc/systemd/zram-generator.conf <<'EOF'
[zram0]
zram-size = min(ram / 2, 16384)
compression-algorithm = zstd
swap-priority = 100
EOF
```

| Параметр | Значение | Почему так |
| :--- | :--- | :--- |
| `zram-size = min(ram / 2, 16384)` | Половина RAM, но не больше 16 ГБ | Для 32 ГБ RAM это даст 16 ГБ ZRAM — с запасом. `min()` защищает от абсурдных значений на машинах с 128+ ГБ RAM: ZRAM там не нужен в размере 64 ГБ. |
| `compression-algorithm = zstd` | zstd | Лучший баланс степень сжатия / скорость. `lzo-rle` быстрее, но сжимает хуже; `zstd` на i5-11400 (Rocket Lake, AVX-512) даёт хороший результат при минимальной нагрузке. |
| `swap-priority = 100` | Высокий приоритет | Ядро будет предпочитать ZRAM дисковому swap (если он вообще появится). Это правильно: ZRAM быстрее. |

> [!info] Нужен ли дисковый swap
> С ZRAM на 16 ГБ и 32 ГБ RAM дисковый swap, скорее всего, не понадобится. Но при необходимости подстраховаться (например, для гибернации) можно добавить swap-файл на LUKS-разделе.
> Это делается отдельно и не входит в базовую поставку.

### 🔑 Этап 4.7: Настройка opendoas

`opendoas` — минималистичная замена `sudo` (около 1000 строк кода против десятков тысяч у `sudo`). В Ubuntu 26.04 пакет `opendoas` **не создаёт** `/etc/doas.conf` автоматически; без конфигурационного файла `doas` отказывает всем без объяснений. Поэтому конфиг создаётся вручную сразу после установки пакета.

Первым делом создаётся группа `wheel`. В Debian и Ubuntu исторически использовалась группа `sudo`, а группа `wheel` (стандарт для BSD и RHEL) по умолчанию отсутствует. Поскольку `opendoas` пришёл из мира BSD и ожидает `wheel`, её нужно создать явно:

```bash
groupadd -f wheel
```

Флаг `-f` (force) делает команду идемпотентной: если группа `wheel` вдруг уже существует, ошибки не будет.

Теперь создаётся конфигурационный файл:

```bash
cat > /etc/doas.conf <<'EOF'
permit persist setenv { PATH XAUTHORITY LANG LC_ALL } :wheel
EOF
chmod 0400 /etc/doas.conf
```

**Почему именно так:**

| Директива | Значение | Почему так |
| :--- | :--- | :--- |
| `permit` | Разрешение | Основная директива: «разрешить выполнение». |
| `persist` | Не спрашивать пароль повторно | Аналог `sudo` с таймаутом. Удобно при серии команд. В Linux-порте реализован через timestamp-файлы, а не через API ядра, поэтому для строгих окружений его лучше убрать. |
| `setenv { ... }` | Сохранять только указанные переменные | Без `XAUTHORITY` не будут работать графические приложения через `doas`; без `LANG`/`LC_ALL` можно получить неправильную локаль. `PATH` сохраняется, чтобы `doas` находил те же команды, что и ваша оболочка. |
| `:wheel` | Группа wheel | Все члены группы `wheel` получают право на `doas`. |

Права `0400` на `/etc/doas.conf` обязательны: `doas` откажется работать с более широкими правами, потому что конфиг содержит правила безопасности.

> [!tip] Если нужна прозрачная замена `sudo`
> Можно создать симлинк:
>
> ```bash
> ln -s "$(command -v doas)" /usr/local/bin/sudo
> ```
>
> Но это работает только для базового `sudo <command>`.
> Все флаги (`-i`, `-s`, `-E`, `-u`, `-g`, `-H`, `-k`, `-K`) либо отсутствуют, либо ведут себя иначе.
> Симлинк оправдан только в простых окружениях; для станции с разнообразными скриптами предпочтительнее явное использование `doas` без маскировки под `sudo`.

### 🌍 Этап 4.8: Локали, время и раскладка консоли

Этап 4.1 и 4.2 настроили графическое окружение для Wayland. Однако текстовая консоль (TTY) и системные сервисы (включая логи и почту) используют собственные настройки локали и раскладки. Без их явной конфигурации система загрузится с дефолтной локалью `C` (что означает английский язык, но без поддержки UTF-8, что может сломать вывод кириллицы в терминале) и стандартной раскладкой `us`.

Для начала настраиваются локали. Пакет `locales` уже установлен на Этапе 3.4. Нужно сгенерировать требуемые локали и установить системную по умолчанию:

```bash
cat > /etc/locale.gen <<'EOF'
en_US.UTF-8 UTF-8
ru_RU.UTF-8 UTF-8
EOF

locale-gen
update-locale LANG=en_US.UTF-8
```

Английский язык выбран системным (`LANG=en_US.UTF-8`), потому что все системные сообщения, логи и ошибки будут на английском — это стандарт для DevOps-станций и упрощает поиск решений в интернете. Русская локаль сгенерирована для корректного отображения дат, форматов чисел и работы приложений, которые её требуют.

Далее настраивается часовой пояс и синхронизация времени. Симлинк определяет зону, а `timedatectl` активирует службу `systemd-timesyncd` (пакет установлен на Этапе 3.4) для автоматической синхронизации.

```bash
# Установка часового пояса (пример для Москвы)
ln -sf /usr/share/zoneinfo/Europe/Moscow /etc/localtime

# Включение синхронизации времени по NTP
systemctl enable systemd-timesyncd
timedatectl set-ntp true

# Сохранение текущего времени в аппаратные часы (RTC)
hwclock --systohc
```

> [!info] Аппаратные часы (RTC) в UTC
> По умолчанию Linux хранит время в RTC в UTC, а локальное время вычисляет по часовому поясу.
> `hwclock --systohc` запишет текущее системное время (уже с учётом пояса) в RTC в формате UTC.
> Если на этой же машине установлена Windows, её нужно настроить на использование UTC (через реестр), иначе время будет сбиваться при переключении между ОС.

### 🏷️ Этап 4.9: Имя хоста и файл hosts

`debootstrap` присваивает системе имя `ubuntu`. Для рабочей станции лучше задать уникальное имя, чтобы оно корректно отображалось в сети, в логах и в приглашении терминала.

```bash
# Задаем имя хоста (пример: ustation - Ubuntu Station)
echo "ustation" > /etc/hostname

# Прописываем localhost и имя хоста в /etc/hosts
cat > /etc/hosts <<'EOF'
127.0.0.1       localhost
127.0.1.1       ustation

::1             localhost ip6-localhost ip6-loopback
ff02::1         ip6-allnodes
ff02::2         ip6-allrouters
EOF
```

> [!warning] Важность `/etc/hosts`
> Если не прописать имя хоста в `/etc/hosts`, некоторые программы будут долго искать DNS-запись для собственного имени, что приводит к задержкам при запуске и работе.
> Строка `127.0.1.1` — стандартный способ решить это без реального DNS.

### 👤 Этап 4.10: Создание пользователей и групп

К этому моменту система настроена, но в ней нет ни одного пользователя, кроме `root`, и у `root` нет пароля (он изначально заблокирован в `debootstrap`). Оставлять систему в таком состоянии нельзя — войти в неё будет невозможно. Этот шаг создаёт рабочую учётную запись и настраивает права.

В отличие от многих руководств, мы **сознательно оставляем учётную запись `root` заблокированной**. Вход под `root` напрямую не только не нужен, но и вреден: он снижает безопасность (нет журнала аудита конкретных действий пользователя), повышает риск случайно сломать систему одной неверной командой и создаёт дополнительную цель для атак, если на машине когда-либо поднимется SSH-сервер. Вместо этого всё администрирование выполняется через `doas`, который логирует, *кто именно* и *какую команду* запустил от имени суперпользователя.

Для явной фиксации этого решения блокируем пароль `root`:

```bash
passwd -l root
```

> [!question] Зачем нужен `passwd -l root`, если пароля и так нет?
> `debootstrap` создаёт запись `root` в `/etc/shadow` с маркером `!` или `*` (заблокировано).
> Команда `passwd -l root` гарантирует это состояние, даже если до этого вы случайно установили пароль.
> Если в будущем потребуется войти под `root` (например, для восстановления системы), это можно сделать через загрузку с параметром ядра `init=/bin/bash` или через LiveUSB.

Теперь создаётся ежедневный пользователь. Мы используем `useradd` вместо `adduser`, потому что `useradd` детерминирован и не задаёт интерактивных вопросов, что идеально для скриптовой сборки.

```bash
# Замените <username> на желаемое имя пользователя
useradd -m -s /bin/bash -G wheel,netdev,audio,video,input,render <username>
passwd <username>
```

> [!danger] Критически важна группа `wheel`
> Поскольку вход под `root` заблокирован, пользователь **обязан** состоять в группе `wheel`.
> В конфигурации `doas` из Этапа 4.7 указано правило `permit persist setenv { ... } :wheel`, и если пользователя нет в этой группе, он не сможет повышать привилегии.
> В этом случае вы окажетесь в системе без прав администратора, и для исправления потребуется загрузка с LiveUSB.
>
> Помимо `wheel`, добавляются и другие группы:
> - **`netdev`** — необходима для управления `wpa_supplicant` через `wpa_cli`. В конфиге `/etc/wpa_supplicant/wpa_supplicant-wlp3s0.conf` указано `GROUP=netdev` (Этап 4.3).
> - **`audio`, `video`, `input`, `render`** — доступ к звуковым устройствам (`/dev/snd/*`), видеокарте (`/dev/dri/*`), устройствам ввода (`/dev/input/*`).
> В Wayland-сессиях `systemd-logind` часто выдаёт права динамически через ACL, но наличие групп — надёжный fallback, если что-то пойдёт не так.

После создания пользователя проверяется, что все группы применились:

```bash
id <username>
```

Вывод должен содержать полный список групп, включая `wheel` и `netdev`.

## 🚀 Этап 5: Загрузчик, Secure Boot и резервное копирование

Этот этап связывает собранную систему с аппаратной платформой. До сих пор все действия происходили внутри `chroot` и не влияли на способность машины загрузиться. Теперь создаётся загрузчик, регистрируется ключ для Secure Boot (критично для будущих DKMS-модулей Nvidia), настраивается графическая загрузка и автоматизируется резервное копирование. Ошибка на этом этапе может привести к тому, что система не загрузится, поэтому команды выполняются в строго определённом порядке.

### 🖼️ Этап 5.1: Загрузчик GRUB

GRUB для UEFI-системы требует установки в EFI-раздел и генерации конфигурации. Основное решение здесь — параметры `GRUB_DEFAULT=saved` и `GRUB_SAVEDEFAULT=true`. Они заставляют GRUB запоминать последнее успешно загруженное ядро. Если после обновления новое ядро окажется неработоспособным (например, конфликт с драйвером Nvidia), вы сможете один раз выбрать старое ядро в меню, и оно станет дефолтным при следующей загрузке.

Для начала нужно перенести тему оформления в загрузочный раздел. Пакет `grub-theme-breeze` распаковывает файлы в `/usr/share/grub/themes/breeze/`. Поскольку `/usr` находится в зашифрованном LUKS-контейнере, GRUB не сможет прочитать оттуда тему при загрузке. Поэтому файлы копируются на незашифрованный раздел `/boot`, который доступен загрузчику:

```bash
mkdir -p /boot/grub/themes
cp -r /usr/share/grub/themes/breeze /boot/grub/themes/
```

Теперь настройки фиксируются в `/etc/default/grub`:

```bash
cat > /etc/default/grub <<'EOF'
GRUB_DEFAULT=saved
GRUB_SAVEDEFAULT=true
GRUB_TIMEOUT=10
GRUB_TIMEOUT_STYLE=menu
GRUB_DISTRIBUTOR=`lsb_release -i -s 2> /dev/null || echo Debian`
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"
GRUB_CMDLINE_LINUX=""
GRUB_DISABLE_RECOVERY=true
GRUB_THEME="/boot/grub/themes/breeze/theme.txt"
EOF
```

Параметр `GRUB_TIMEOUT=10` даёт десять секунд на выбор пункта меню. `GRUB_DISABLE_RECOVERY=true` убирает лишние пункты Recovery Mode (у нас есть LiveUSB). `GRUB_THEME` указывает на скопированную тему. Параметр `GRUB_CMDLINE_LINUX_DEFAULT="quiet splash"` скрывает отладочный вывод ядра и включает Plymouth.

После записи конфигурации загрузчик устанавливается в EFI-раздел, генерируются файлы конфигурации и пересобирается `initramfs`:

```bash
# Установка загрузчика (флаг --uefi-secure-boot гарантирует совместимость с SB)
grub-install --target=x86_64-efi --efi-directory=/boot/efi --bootloader-id=ubuntu --uefi-secure-boot --recheck

# Генерация grub.cfg
update-grub

# Пересборка initramfs для всех установленных ядер (важно: подхватит настройки LUKS и Plymouth)
update-initramfs -u -k all
```

Порядок команд строго фиксирован: сначала выполняется `grub-install` (записывает бинарники `grubx64.efi` и `shimx64.efi` в ESP), затем `update-grub` (генерирует `/boot/grub/grub.cfg` на основе текущих ядер и настроек), и только потом `update-initramfs` (собирает образы с учётом только что добавленных модулей LUKS и Plymouth). Если поменять местами `grub-install` и `update-grub`, инсталлятор может перезаписать только что созданный конфиг дефолтным.

### 🔐 Этап 5.2: Secure Boot и MOK (Machine Owner Key)

Secure Boot проверяет подпись каждого загружаемого компонента. Загрузчик Ubuntu (`shim-signed`) и ядро (`linux-generic-hwe-26.04`) подписаны ключами Microsoft и Canonical, поэтому загружаются без проблем. Однако драйвер Nvidia (и любые другие DKMS-модули) не подписан этими ключами. При попытке загрузить такой модуль ядро откажется его принимать, и вы получите черный экран или работу через `nouveau`/`llvmpipe`.

Решение — сгенерировать собственный ключ (MOK — Machine Owner Key), подписать им модули Nvidia и зарегистрировать этот ключ в прошивке. Регистрация требует физического подтверждения при следующей перезагрузке (MOK Manager), поэтому она выполняется сейчас, до установки драйвера Nvidia. Ключ генерируется и регистрируется командами:

```bash
# Генерация MOK-ключа (создаст /var/lib/shim-signed/mok/MOK.priv и MOK.der)
mokutil --generate-key

# Регистрация ключа в прошивке (запросит пароль)
mokutil --import /var/lib/shim-signed/mok/MOK.der
```

При выполнении `mokutil --import` система попросит задать пароль. Этот пароль используется **только один раз** при следующей загрузке.

> [!danger] Обязательный шаг после перезагрузки
> После того как вы выполните `exit`, размонтируете разделы и перезагрузитесь, появится синий экран **MOK Manager**.
> Необходимо выбрать `Enroll MOK` → `Continue` → `Yes` → ввести пароль, заданный при `--import` → `Reboot`.
> Если пропустить этот шаг (или случайно выбрать `No`), ключ не зарегистрируется, и модули Nvidia не будут загружаться. В этом случае процедуру `mokutil --import` можно повторить из загруженной системы.

### 📸 Этап 5.3: Экран загрузки Plymouth

Plymouth скрывает текстовый вывод ядра и показывает графическую анимацию. По умолчанию в минимальной сборке может быть выбрана не самая информативная тема, либо тема не настроена вовсе. Мы используем тему `spinner` (или `glow`), которая отображается поверх запроса пароля LUKS. Выбор темы выполняется интерактивно:

```bash
# Выбор темы по умолчанию
update-alternatives --config default.plymouth

# Пересборка initramfs после выбора темы (например, /usr/share/plymouth/themes/spinner/spinner.plymouth)
update-initramfs -u
```

Plymouth не скрывает запрос пароля LUKS, а отображает его поверх выбранной темы. Если вы отлаживаете проблемы с загрузкой, параметр `splash` из `/etc/default/grub` временно убирается, чтобы видеть системные сообщения.

## 🚀 Этап 6: Финализация и первая загрузка

Базовая система собрана и настроена. Вы сделали 99% работы: создан пользователь, настроены сеть, загрузчик и Secure Boot. Осталось только очистить кэш, выйти из `chroot`, отмонтировать разделы и загрузиться в новую систему.

Первым делом удаляем скачанные архивы пакетов и временный мусор, чтобы они не занимали место в итоговом образе:

```bash
apt clean
apt autoremove --purge -y
```

Теперь всё готово к выходу. Выполните выход из `chroot`, рекурсивно отмонтируйте все разделы (включая вложенные `/boot`, `/boot/efi` и `/sys`), закройте LUKS-контейнер и перезагрузитесь:

```bash
# Выход из chroot
exit

# Отмонтируем все разделы (ключ -R рекурсивно размонтирует вложенные точки)
sudo umount -R /mnt

# Закрываем LUKS-контейнер
sudo cryptsetup close --deferred cryptroot

# Перезагрузка
sudo reboot
```

> [!danger] Не пропустите MOK Manager!
> Если на Этапе 5.2 вы выполнили `mokutil --import`, то при первой перезагрузке (сразу после `reboot`) до меню GRUB появится синий экран **MOK Manager**.
> Вам нужно:
> 1. Выбрать `Enroll MOK` → `Continue` → `Yes`.
> 2. Ввести пароль, который вы задавали при `--import`.
> 3. Выбрать `Reboot`.
> 
> Если вы случайно нажали `No` или не успели, система загрузится без ключа. В этом случае вы сможете повторить процедуру позже из-под своей учетной записи (`doas mokutil --import /var/lib/shim-signed/mok/MOK.der`) и снова перезагрузиться.

После регистрации ключа или перезагрузки вы увидите запрос пароля для расшифровки LUKS (помните, что он вводится в консольной раскладке `us`), затем анимацию Plymouth (spinner) и, наконец, черный экран с приглашением `login:`. 

Войдите под созданным пользователем (вход под `root` заблокирован). Сразу после входа проверьте базовую работоспособность системы:

```bash
# Проверка прав doas (должно вывести uid=0(root))
doas id

# Проверка сети и Wi-Fi
ip a
networkctl status wlp3s0
ping -c 3 1.1.1.1

# Проверка сетевого тюнинга (BBR) и сжатого swap (ZRAM)
sysctl net.ipv4.tcp_congestion_control  # ожидаем bbr
zramctl                                 # ожидаем /dev/zram0
```

Поздравляю, базовая hardened-система готова и успешно загружена! Следующий этап — установка проприетарного драйвера Nvidia, настройка пользовательского окружения (Qtile, S6) и установка повседневного софта.

### 🟢 Этап 7.1: Установка драйвера Nvidia и исправление генерации MOK

Изначально в документации предлагалось использовать репозиторий NVIDIA и открытые модули `nvidia-open`. Однако на практике выяснилось, что драйверы из репозитория NVIDIA (версия 615.71.10) не собираются с ядром Linux 7.0 из-за ошибки `cxlds incomplete type`. 

К счастью, компания Canonical уже включила необходимые патчи в свои официальные пакеты. Поэтому мы будем использовать драйверы из стандартного репозитория Ubuntu (версия 615.71.09-0ubuntu0.26.04.2), которые собираются «из коробки». Пакет `nvidia-driver-610` в Ubuntu 26.04 является транзитивным (переходным) и автоматически подтянет актуальную ветку 615 с уже примененными патчами. Также мы **не будем устанавливать 32-битные библиотеки (i386)**, так как они нужны только для Steam/Wine, а для DevOps-станции это лишняя поверхность атаки.

Если на Этапе 5.2 вы пропустили генерацию ключа MOK (Machine Owner Key), сейчас самое время это исправить. В современных версиях `mokutil` нет команды `--generate-key`, поэтому ключ создается через `openssl`:

```bash
# Создаем директорию для ключей
doas mkdir -p /var/lib/shim-signed/mok/

# Генерируем ключ и сертификат (введите пароль и запомните его)
doas openssl req -new -x509 -newkey rsa:2048 -keyout /var/lib/shim-signed/mok/MOK.priv -outform DER -out /var/lib/shim-signed/mok/MOK.der -nodes -days 3650 -subj "/CN=My MOK/"

# Импортируем сертификат в прошивку (запросит тот же пароль)
doas mokutil --import /var/lib/shim-signed/mok/MOK.der
```

После импорта ключа нужно будет перезагрузиться и подтвердить его в синем меню MOK Manager (как описано в Этапе 5.2).

Теперь переходим к установке драйвера. Устанавливаем заголовки ядра, компилятор и сам драйвер из официального репозитория Ubuntu:

```bash
doas apt update
doas apt install -y build-essential linux-headers-$(uname -r)
doas apt install -y nvidia-driver-610
```

В процессе установки DKMS автоматически применит патчи Canonical (`buildfix_kernel_7_0-cxl_structs.patch` и др.) и подпишет собранные модули вашим ключом MOK. После завершения установки перезагрузите систему (`doas reboot`), пройдите процедуру регистрации ключа в MOK Manager (если еще не сделали этого) и проверьте работу драйвера командой `nvidia-smi`.

### 📦 Этап 7.2: Виртуализация (libvirt / KVM)

Для запуска виртуальных машин на базе QEMU/KVM мы установим набор пакетов `libvirt`. Он включает в себя демон управления, утилиты командной строки (`virsh`), графический интерфейс `virt-manager`, а также пакеты для поддержки UEFI в виртуальных машинах (`ovmf`) и сетевой изоляции (`dnsmasq-base`).

Выполните установку:
```bash
doas apt install -y qemu-system-x86 qemu-utils libvirt-daemon-system libvirt-clients virt-manager virtinst bridge-utils cpu-checker ovmf qemu-system-gui dnsmasq-base libxml2-utils
```

После установки проверьте, что ваш процессор поддерживает аппаратную виртуализацию:
```bash
kvm-ok
```
Ожидаемый вывод: `INFO: /dev/kvm exists` и `KVM acceleration can be used`.

Затем включите и запустите службу `libvirtd`:
```bash
doas systemctl enable --now libvirtd
```

Чтобы управлять виртуальными машинами без постоянного ввода пароля `doas`, добавьте вашего пользователя в группы `libvirt` и `kvm`. Изменения вступят в силу только после полного выхода из системы и повторного входа (или перезагрузки):
```bash
doas usermod -aG libvirt,kvm $USER
```

Настройте сеть по умолчанию (NAT) для выхода виртуальных машин в интернет и добавьте её в автозагрузку:
```bash
doas virsh net-start default
doas virsh net-autostart default
```

Для комплексной проверки хоста выполните `doas virt-host-validate qemu`. Все проверки (VirtIO, IOMMU и т.д.) должны завершиться статусом `PASS`. Предупреждение `WARN (None of SEV, SEV-ES, SEV-SNP, TDX available)` можно игнорировать — это серверные технологии конфиденциальных вычислений, которых нет в потребительских процессорах Intel Core.

### 🐳 Этап 7.3: Контейнеры (Rootful nerdctl + containerd + BuildKit)

Изначально мы пытались использовать `nerdctl` в rootless-режиме для повышения безопасности. Однако на практике rootless-режим показал себя нестабильным в вопросах логирования (постоянные ошибки `broken pipe` и `ttrpc: closed` при завершении коротких контейнеров). Для личной станции, где приоритет отдается удобству и предсказуемости, мы переходим на системный (rootful) режим. 

**Внимание:** В этом режиме контейнеры запускаются от имени `root`, поэтому не запускайте образы из непроверенных источников.

Сначала установим сам демон `containerd`:
```bash
doas apt install -y containerd
```

На Этапе 1 мы создали отдельный LVM-том `/var/lib/containers`. Настроим системный `containerd`, чтобы он хранил образы и слои именно там, а не забивал системный раздел:
```bash
doas mkdir -p /etc/containerd
doas tee /etc/containerd/config.toml > /dev/null <<'EOF'
version = 2
root = "/var/lib/containers/containerd"
state = "/run/containerd"
EOF
doas chown -R root:root /var/lib/containers
doas systemctl enable --now containerd
```

Скачаем и распакуем `nerdctl-full` (включает в себя CLI, `buildkit` и `runc`):
```bash
wget https://github.com/containerd/nerdctl/releases/download/v2.4.2/nerdctl-full-2.4.2-linux-amd64.tar.gz
doas tar -C /usr/local -xzf nerdctl-full-2.4.2-linux-amd64.tar.gz
```

Теперь настроим демон `BuildKit`, который используется для сборки образов. Создадим для него конфигурационный файл, указав путь к нашему LVM-тому и подключив его к системному `containerd`:
```bash
doas mkdir -p /etc/buildkit
doas tee /etc/buildkit/buildkitd.toml > /dev/null <<'EOF'
root = "/var/lib/containers/buildkit"

[worker.oci]
  enabled = false

[worker.containerd]
  enabled = true
  address = "/run/containerd/containerd.sock"
  namespace = "default"
EOF

doas mkdir -p /var/lib/containers/buildkit
doas chown -R root:root /var/lib/containers/buildkit
```

Создадим и запустим systemd-сервис для `BuildKit`:
```bash
doas tee /etc/systemd/system/buildkit.service > /dev/null <<'EOF'
[Unit]
Description=BuildKit
Documentation=https://github.com/moby/buildkit
After=network.target containerd.service

[Service]
Type=notify
ExecStart=/usr/local/bin/buildkitd --config /etc/buildkit/buildkitd.toml
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

doas systemctl daemon-reload
doas systemctl enable --now buildkit
```

Поскольку `nerdctl` теперь работает с системным сокетом от имени `root`, вам придется вызывать его через `doas`. Чтобы не писать это каждый раз, создайте удобные алиасы в вашем `~/.bashrc`:
```bash
echo "alias docker='doas nerdctl'" >> ~/.bashrc
echo "alias nerdctl='doas nerdctl'" >> ~/.bashrc
source ~/.bashrc
```

Проверьте работу контейнеров, запустив классический тест. На этот раз вывод должен быть абсолютно чистым, без ошибок логирования:
```bash
nerdctl run --rm hello-world
```
